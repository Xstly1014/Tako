# 增量 A 业务复盘 · 2026-10-30

A 已交付真实环境中的邮箱登录与可靠私密草稿，核心链路有实际证据；真机粘贴和 Wi-Fi／蜂窝切换仍待补测。它解决了创作者把文字交给平台时的基础信任问题，尚未验证社区吸引力或用户留存，不能称为公开运营首版。

本次复盘重新核对了[业务共识](../../项目业务共识.html)、[开发规格](../../增量A开发规格.html)、[最终验收记录](2026-10-30-a-acceptance.md)，并按 [business-first](../../.agents/skills/business-first/SKILL.md) 的失败、并发、持久化、契约、可观测和范围克制标准检查。历史阶段记录保留当时事实，以当前验收范围为准。

## 背景与要兑现的需求

Tako 希望服务有表达欲的用户，初期通过校园渠道接近大学生，由开发者亲自运营。短内容容纳日常、吐槽、灵感和分享；中篇承载完整故事或情绪；长篇承载幻想、冒险和连载。品牌采用年轻、多元的二次元视觉，题材不限定为文艺表达。

项目目标包含治理风控、内容消费、增长和商业化，但第一阶段没有用户规模，也没有必要为这些远期方向堆叠中间件。我们把首个增量限定为“真实收码登录 → 写作 → 数据库确认 → 关闭重开 → 故障后恢复”。先保证作者愿意交付文字，再检验作品是否值得阅读、能否被发现。

这里最重要的承诺是：保存状态可信；旧请求不能覆盖新文字；设备冲突不要求作者牺牲一份内容；私密草稿不能被其他账号获取；服务出错后能知道、能恢复。草稿删除、完全离线启动、公开发布和支付没有混入 A。

## 做了什么，怎样证明

| 作者或运营者的问题 | 采用的策略 | 验收证据与适用边界 |
|---|---|---|
| 页面显示成功，文字是否真的留下了？ | 事务提交后返回修订和保存时间；旧响应只确认对应输入 | 用户确认关闭重开完整，ECS 应用重启后数据指纹一致；同步自动测试覆盖旧响应，不能据此承诺整机故障零丢失 |
| 弱网重试会不会重复写，手机会不会盖掉电脑？ | mutation_id 幂等、基础修订校验、冲突自动另存双方 | 真实 MySQL 并发/幂等测试；实际 iPhone 服务断链期间输入，电脑保存新版，恢复后用户确认两份完整且可重开 |
| 掉线、会话过期和退出会不会清空文字？ | IndexedDB 按账号保护，原账号重登恢复；失败不假报已保存，支持导出 | 同步单测与浏览器夹具覆盖恢复和失败；真机完成服务断链与后台返回。存储清除仍可能丢失未同步文字，完整离线启动不保证 |
| 能否真正收到验证码？ | Resend、加密持久化队列、持续 worker、重试与过期判断 | 用户实际收件并登录本机和 ECS；服务商接受不等于送达，目前测试发件配置仍只覆盖本人收件 |
| 别人的账号能否拿走草稿？ | 每次资源操作由服务端会话检查归属；来源保护与安全 Cookie | 真实数据库/HTTP 契约反例验证；未冒称两个外部真实用户完成收件验收 |
| 机器坏了怎么办？ | ECS 外加密 OSS 备份，私有 ACL、匿名拒绝、往返校验与独立恢复 | 最终 2 份草稿、9 个修订、9 张业务/迁移表全字段指纹一致，两次恢复约 22/18 秒；这是小库数据库恢复，不是整机恢复 SLA |
| 故障是否只能等用户投诉？ | 独立监控任务检查进程、备份时效与失败，去重通知并发送恢复邮件 | 维护进程与备份逾期演练；用户确认收到实际故障/恢复通知。整机失联仍需主机外探针 |

已交付 Go 模块化单体、MySQL 迁移、Nuxt 私密写作空间、OpenAPI/Swagger、后台任务、恢复工具、ECS 私有部署与运维说明。自动化包括真实 MySQL/race/契约测试、12 项同步测试和 8 项 Chromium 场景；浏览器 API 夹具与真机、外部服务验收分别记账，不相互替代。

## 遇到的问题与纠正

**接口先实现、契约后补，确实出现了 demo 化倾向。** 用户指出 Swagger 缺失后，我们把 OpenAPI 设为唯一 HTTP 契约，补请求/响应校验、路由覆盖和错误语义。Swagger 页面本身不代表业务完整，保存冲突、依赖故障和权限反例才是契约能否承接业务的检验。

**单封测试邮件成功，被过早当成登录链路成功。** 页面请求入队后，缺少持续 worker 就无法发送。后来补齐独立进程、启动说明和监控，并回到页面让用户实际申请、收件、登录。这是交付检查遗漏，不能归因于服务商。以后验收完整用户动作和进程依赖，而不是只验证适配器。

**测试与用户数据需要隔离。** 发现清理类测试存在接触业务库的风险后，改为独立 writing_test 数据库和迁移流程。真实数据库测试有必要，但不能以测试之名影响用户文字；也不能没有证据就声称历史操作从未有风险。

**权限配置和私密性不能靠口头确认。** OSS 最初只有上传/下载权限，新增 ACL 操作仍被拒绝；核对完整 RAM 策略后，才确认四项对象权限和限定前缀。还发现备份对象匿名可读，立即暂停相关自动化，只修正备份对象权限，再把 private ACL 与匿名 403 纳入成功条件。对象是加密归档，没有上传密钥或明文；这不代表可以证明此前无人访问。没有因此放宽为全桶权限。

**电脑可访问不等于手机可访问。** Tailscale 遇到 App Store 地区限制，Docker 热点转发也未打通真机。最终用原生 Caddy、开发证书、限定地址规则和 SSH 私有通路完成实际 iPhone 验收，结束后清理。这个临时方案成本较高；今后先核对设备可安装性与访问路径，优先稳定 HTTPS 测试入口，减少旁路工程。

**“全部完成”的表述比证据走得快。** 复核原规格才发现粘贴与 Wi-Fi／蜂窝切换未单独记录，服务断链也不等于网络切换。用户选择将其列为尾项，稳定 HTTPS 入口就绪后补测。开发规格里过时的数分钟恢复点目标也已改成实际选择的每日备份。不能为了收口而降低原承诺，或者把没有测过写成通过。

**视觉表达曾偏离目标用户。** 早期清新文艺文案与用户期望的日常、多元和二次元品牌不一致，已改为直接的创作入口、蓝色视觉与原创看板娘。README 现在展示实际首页，而不是只展示技术栈。此举修正定位，不等于已证明更受用户欢迎，仍需真实用户反馈。

## 关键取舍是否合理

- 冲突另存而不自动合并：保护作者内容与选择权，代价是需要整理副本；目前没有实时协作需求，不引入复杂合并系统。
- 每日备份、保留 30 天：用户在预算和当前数据规模下明确选择。正常离机恢复点约一天，失败会更久并告警；数据库保存成功与离机备份完成分开表述。未来作者投入增加时要重新讨论频率。
- 模块化单体和现成组件：把事务、幂等、权限与恢复做到当前需求所需程度，暂不引入 Redis、独立 MQ、微服务或 Kubernetes。后台进程拆开不等于已实现分布式高可用。
- 小机器离线构建、私有云端测试：适应 2 vCPU／2 GiB 资源，不把本机 Compose 当生产方案。公开接入和外部注册条件未就绪，就不提前宣发。

A 的基础设施投入已经足以支持下一条业务链路，继续美化技术中台会挤占内容业务验证时间。下一阶段应优先评审和实现一篇完整中篇的发布、稳定链接阅读、隐藏与恢复，并在开放范围前具备相应最小治理能力。

| 优先级 | 缺口 | 退出条件 |

| P1 · 公开测试门槛 | 域名实名/备案/DNS/HTTPS、自有发信域名、主机外探针 | 实际外部访问、授权测试收件、整机不可达告警均留证据后再邀请公开注册 |
| P1 · 运维诊断 | 备份失败摘要仍偏粗，容量与恢复规模证据有限 | 引入无敏感信息的分阶段错误码；随数据增长补代表性恢复演练，不能用小样本外推 |
| P1 · 依赖维护 | 7 项低危传递依赖和打包器 override | B 公网内测前复核可兼容升级并运行检查；不以强制降级掩盖问题 |
| 后续业务增量 | 发布、阅读、隐藏恢复、反馈、治理和发现 | 逐条冻结行为与失败语义，再以真实用户动作验收；不能靠页面占位算交付 |

OSS 30 天生命周期由用户配置，尚未经历自然到期删除；需在首批对象到期后核对规则实际执行。私有部署不提供整机高可用，也没有规模流量、高并发或增长成绩。

## 下一轮怎样检验业务价值

目前验收参与者主要是开发者本人，还没有校园招募或真实留存数据。不能把测试草稿数写成用户增长成果。

B 应围绕一个实际作者完成作品、一个实际读者打开稳定链接阅读的过程收集反馈：作者能否独立完成发布，读者能否理解作品并读完，作者是否愿意回来继续创作。保存失败率、未同步滞留、冲突恢复结果继续作为质量指标，不采集正文。阅读/回访指标待行为和统计口径明确后再实现，不凭空设一个“成功增长率”。

当前可以交付的是一套有恢复证据的私密写作基础。社区的价值仍需靠内容、运营和人与人的反馈来证明。
