# A 之后的业务复盘：发布、版本、人工治理与自主注册

日期：2026-10-30。承接 [增量 A 业务复盘](2026-10-30-a-business-review.md)，核对 [B 业务规格](../increment-b-review.md)、各阶段设计及验收记录。本文记录截至本次提交的事实；规格已确认、代码已实现、工程已验证、真实用户结果分别记账。

## 1. 背景：文字保存之后，作者为什么还需要 Tako

A 解决的是作者敢不敢在这里写：私密纯文本、明确的服务端保存确认、断网暂存、冲突保留双方、历史恢复与备份。A 的真机粘贴及实际 Wi-Fi/蜂窝切换仍搁置，没有因为进入 B 就自动验收。

产品目标是面向表达欲强的年轻用户，让短内容、中篇与长篇互相连接。早期潜在用户主要来自校园，运营者愿意亲自运营；当前不收费，先验证创作、消费与反馈。Go 是主要开发语言，技术复杂度要由真实业务约束驱动。

B 要解决的是：作者能把一份明确的文字交给读者，后续继续改稿而不误改公开作品；作者与平台改变可见性时，读者权限有确定结果；平台处理内容时，作者知道原因且有纠错入口。当前真正实现的是中篇纯文本，不把未来短内容、长篇、推荐、商业化当成交付。

## 2. 需求如何落地，以及为什么这样拆

| 链路 | 真实问题 | 已交付策略 | 可观察结果 |
|---|---|---|---|
| B1：固定预览 → 发布 → 阅读 | 草稿仍在自动保存，作者确认后不能发布成另一份内容；网络重试不能变成多个版本 | 固定已保存修订、独立预览、不可变正式版本；消费预览、版本、后审任务及请求确认同事务提交；稳定作品链接 | 草稿更新后旧预览仍明确发布旧稿；重复确认只有一份正式版本；匿名可读正式正文 |
| B2：正式版本与公开范围 | 作者改稿、切换、隐藏与平台限制不能互相覆盖；读者不能通过旧链接拿到已撤权内容 | 工作稿与正式版分离；展示指针、隐藏、历史开关、平台限制独立；预期状态号与幂等确认 | 用户确认新修订、切回旧版、历史开关、隐藏恢复正常，工作稿保留 |
| B3.1：人工后审 → 处置 → 复核 → 纠错 | 后审任务虽已落库，但缺少能操作的处置与解释；误判不能只有封禁、没有出口 | 固定正式版审核；版本/作品处置有范围与原因；同一处置一条在途文字复核；维持后 24 小时冷静期，运营仍可主动撤销 | 用户确认处置、申请、维持与冷静期、主动撤销及读者权限符合预期 |
| 自主注册：取消邮件前置 | 测试发件域名只可向特定邮箱发送，朋友无法自主进入；匿名按旧邮箱设置密码会接管账号 | 无邀请、无邮件验证的邮箱密码注册；bcrypt 与既有会话；旧账号本人登录后首次设密；服务端关闭验证码路径 | 隔离环境新用户注册、保存、重登通过；用户确认原账号重登及旧内容正常 |

这几条链路有工程和用户本人操作证据，但尚未形成“外部作者发布 → 被其他读者发现 → 留下反馈 → 作者回来”的社区闭环。

## 3. 遇到的问题、策略与如何证明有效

### 发布成功与页面收到成功不是一回事

服务器可能已提交，浏览器却断线。直接重新生成请求会重复发布，单纯禁用按钮也解决不了刷新和多设备问题。B1/B2/B3.1 都把请求确认与业务变化放在同一事务；重试先查原确认，过时的新动作再由状态号拒绝。

验证使用真实 MySQL 并发及真实浏览器：让服务器提交后故意丢掉响应，再检查重复提交的结果和数据库条数；注入事件或审计写入失败，确认业务状态一并回滚。这里验证的是已定义竞争和故障分支，不是实际互联网流量下的性能结论。

### “恢复”不能把别人的决定一并抹掉

作者恢复公开不能解除平台限制；运营撤销处置不能取消作者隐藏；审核不能覆盖工作稿；最新版受限不能默默回退旧版。因此这些状态没有合成一个模糊的“是否可见”字段，每个动作只改变自己的责任范围。

验证包括隐藏中发布、恢复默认最新正式版、受限最新版显式选择健康旧版、撤销一条处置但保留其他有效限制。读者 SSR 与 API 都重新判权，隐藏后的 HTML 不包含私密标题正文。已加载阅读可完成，不等于后续请求拥有永久续读权限。

### 治理有权限边界，也必须有纠错解释

运营白名单由服务端配置，普通作者不能调用运营写接口；审核只能读实际提交的固定正式版，不能借审核入口读取私人工作稿。处置必须有原因，主动撤销也要让作者看到原因与时间。

验证覆盖未登录、普通账号、跨作者、并发复核、冷静期到期边界、审计失败回滚及读者访问恢复。浏览器回归还发现“上一条成功提示”可能让人误以为本次已完成，已在切换记录和发起新操作时清除旧提示。验收必须等待本次新结果，并核对实际权限。

目前没有真实违规、误判和复发样本。7 天观察期、48 小时处理目标和自动灌水规则属于制度设计或后续范围；不能由这些参数推导治理有效。B3.1 的人工闭环是能力交付，治理绩效尚无证据。

### 无验证注册是一项产品取舍，不是取消身份保护

用户明确选择早期朋友测试不做邀请、不强制邮箱验证。实现仍保留独立账号、密码散列、会话、同源、必要限频与资源归属检查。重复邮箱不能覆盖旧账号；邮箱未验证不能用于找回或合并；旧账号只能在自己的会话设置密码。

旧 Verify 按邮箱匹配账号，是这一调整里容易遗漏的跨账号风险：仅隐藏验证码按钮不够。密码模式在服务端关闭发送和验证；即使切回旧模式，已有密码的账号也不能通过旧验证码逻辑被接管。测试确认并发注册只产生一个账号，未知账号和错误密码拒绝，旧账号设密保留原 ID。暂不提供找回与改密，不能把这个边界说成完整账号生命周期。

### 构建通过仍然可能交付一个 502

本机更新 API/web 后，Nginx 仍缓存旧容器地址，用户访问账号设置遇到 502。这是交付检查遗漏：隔离测试、构建成功和容器启动没有覆盖用户实际入口。

恢复网关后，配置改为 Docker DNS 动态解析；nginx 配置检查通过，随后再次重建 API，未重启网关仍能访问页面、查询密码模式并确认 OTP 返回 403。原浏览器测试在故障窗口失败，恢复后重新跑，最终 9 项通过。以后更新后的验收必须包含网关入口、静态页面与 API，不能只看构建日志。

## 4. 前端与品牌的复盘

用户要年轻、多元、二次元的品牌，不接受文青文案、低幼化、装饰符号或信息没有重心的工具页。此前反复暴露了三个问题：把原型效果当作真实页面效果；各页面独立编排导致导航无法往返、宽度和锚点跳变；版本号、时间与管理元数据抢占正文焦点。

已接入真实页面的调整包括：Q 版登录形象与闭眼/眨眼等克制交互、作品管理分区、紧凑版本节点、发布与阅读页重排、部分布局稳定性断言。官网继续保留大标题与动态看板娘的张力。

仍需承认：品牌效果没有最终定稿，统一导航也未全站收口；不能把用户同意暂停纠结样式解读为视觉验收通过。已明确将当前宣传页视为官网，另建真正的社区首页。桌面参考起点/B站的分区组织与纵向延伸，手机采用适合内容流的结构；不照搬小说站，也不为了撑满布局制造榜单、封面或虚构数据。

## 5. 顺序上的纠偏：此前做对了什么，做偏了什么

做对的是认真处理了保存、固定发布、状态竞争、权限、幂等与恢复。这些是接入真实数据后不能随意牺牲的约束，不能因为没有运营样本就退回随意覆盖数据的 demo。

做偏的是在读者尚无发现入口时，优先完成较深的版本管理并继续扩张治理规格。用户被吸引来以后，仍可能不知道去哪里读、如何表达反馈。增加更多治理参数不会补上这个缺口。

同行评审提出“能力不是业绩”，这一点成立。也不能反过来把工程测试全部贬成纯夹具：已有真实 MySQL、多账号、并发、断链与恢复证据，它们证明特定行为；外部用户样本证明使用效果。两者各记自己的账，不互相替代。

当前纠偏是暂缓 B3.2，保留已交付人工治理，优先社区发现、收藏和单层评论。评论已经确认合并展示并标记实际阅读版本；来源版本受限时评论仍公开，只关闭版本入口；评论者与作品作者可按权限删除评论，运营独立处理违规评论，没有“撤回评论”操作。以上仍是下一条实现规格，不是已有互动能力。

## 6. 证据账本与最终交付

| 范围 | 代码能力 | 已验证行为 | 真实用户结果 |
|---|---|---|---|
| B1 发布阅读 | 已实现 | MySQL、事务失败、并发、丢响应重试、匿名 SSR 通过 | 用户本人发布及无痕阅读确认；无新增外部发布/阅读样本 |
| B2 版本管理 | 已实现 | 可见性竞争、历史撤权、隐藏恢复、导出与分页通过 | 用户本人操作确认；无外部版本使用效果 |
| B3.1 人工治理 | 最小集已实现 | 独立作者/运营权限、复核、冷静期、撤销及回滚通过 | 用户本人流程确认；无真实治理绩效样本 |
| 自主注册 | 已实现，本机 password 模式 | 真实公开注册 API、浏览器注册保存重登、旧账号迁移通过 | 用户本人确认原账号重登和数据正常；无新增外部自主注册样本 |
| 社区发现/反馈 | 规格已确认主要边界 | 尚未实现完整链路 | 无发现、评论、收藏或回访结果 |

本机当前 schema 10、OpenAPI 0.7.0。API 实现包含契约、运行时校验、路由及响应测试；前端有真实页面和浏览器证据。最近全后端 race/集成/契约及 vet、前端 typecheck/构建、12 项同步单测、9 项草稿浏览器回归通过。

恢复证据随新增数据扩展：B1 为 15 表、B2 为 17 表、B3.1 为 20 表；最新含密码凭据的 21 表在独立 MySQL 容器恢复，全字段指纹一致，30.72 秒。这是小规模本机演练结果，不是生产恢复 SLA，也不是新增 B 数据的 OSS 离机验收。

最终交付的是本地可使用、已验证明确行为的创作/发布/版本/人工纠错及自主注册链路，与规格、API 契约、自动测试、截图、加密恢复记录。ECS 仍是 A/schema 6，没有因为本机升级而自动部署；没有公开上线、付费、推荐算法或高并发高可用成果。

## 7. 还缺什么，下一段怎样验收

| 优先级 | 缺口 | 退出条件 |
|---|---|---|
| 当前 | 真实社区首页与可发现内容 | 官网能进入社区，人工精选/最新发布/真实标签可读；列表不泄露隐藏或受限元数据，切换与返回路径可达；无数据和失败可理解 |
| 当前 | 收藏与单层评论 | 收藏绑定作品且防重复；评论绑定实际阅读版本、可按权限删除；重试和跨账号行为通过；不能只加按钮 |
| 当前链路完成后 | 可访问的私测环境与外部样本 | 单独讨论并落实访问条件，再由非开发者独立注册、发布，另一位读者找到作品并完成收藏或评论；打开页面不记为读完，未观察回访不记为留存 |
| 继续搁置、条件具备再补 | A 真机粘贴与真实切网 | 重新获得稳定真机访问入口后按原场景补测，保持未验收标记 |
| B3.2 暂缓 | 观察期、先审后发、待审替换/驳回、主动超时告警、明确灌水规则 | 在恢复该批次时重新核对业务状态与验收，不以已有表结构或被动超时文案冒充完成 |
| 部署时单独处理 | B 新增数据的 ECS/OSS 兼容、访问与运行检查 | 新环境真实部署、备份恢复与入口检查通过；本地测试和 A 的历史离机记录不自动覆盖 B |

下一段的业务目标是让一篇真实作品被另一位用户找到并留下反馈。先兑现入口与互动，再根据实际样本调整发现和治理；不靠堆叠基础设施或提前宣称企业级规模来丰富项目经历。
