# 跨班次积压对账整包

2026-11-11，Asia/Shanghai。开发基线 `55092a7`，主线 `4d8602b`。业务目标：接班者能核对上一班留下的积压去向，而不是靠两张总数相减判断处置效果。

## 业务规格

入口位于既有运营工作台首页的“跨班次积压对账”。选择扫描时间递增的两个不同班次，冻结双方扫描结果，逐项比较发行前审、发行后审和作者复核三个超时队列。

| 分类 | 定义及限制 |
| --- | --- |
| 继续积压 | 两次完整超时扫描都出现的同队列、同任务标识；按本班快照观察，不宣称此刻仍待处理 |
| 新进入超时 | 只在本班超时扫描出现；不等于本班新创建，可能只是刚超过 48 小时 |
| 离开超时队列 | 只在上班出现；不能直接计作处理完成，需用原始定位回查 |
| 已有决定 | 离开项在回查时间读取到了明确状态，包括通过、限制、维持、撤销、被替换等原状态；不等于读者已经可见 |
| 仍待处理 | 离开项详情仍返回 pending，不能计作已有决定 |
| 未确认 | 读取失败、无权限、限频、缺定位或被替换后的当前稿未确认；不能补零或计作已有决定 |

每队列满足 `上班 + 新进入 - 离开 = 本班`，明细最多每页 20 条。报告完整仅表示离开项均能明确核对，不意味着没有待办。报告保留两班编号、当时修订、扫描时间和逐项回查时间，不将后续读到的决定倒推为在两班之间发生。

两班必须都已完成积压扫描；其他整班阶段未完成不妨碍对完整扫描做对账。相同任务标识绑定不同定位信息时拒绝比较。整班后续续查不会改写已冻结对账。

## 实现与接口

范围限定 `agents/author-support/**`、本端进度和阶段记录，复用 `reviewHandoff` 的现有 GET 和权限验证，不修改产品 API、主开发 Web/App 或共享数据库迁移。

本地命令桥契约版本 1.1.0：

- `POST /local/reconcile {previousId,currentId}`：校验来源，冻结并保存报告，然后异步回查；202 返回 reportId。没有离开项时直接完成，无需发起运营登录。
- `POST /local/resume-reconciliation {id}`：只重试未确认项；已完整报告直接返回 200，不重复登录或读取。
- 既有 `history/report` 的 kind 增加 `reconciliations`，支持倒序游标、详情与跨进程读取。
- 稳定错误：`shift_scan_incomplete`、`shifts_not_comparable`、`reconciliation_target_changed`、`reconciliation_changed` 为 409；缺失资源为 404，非法请求为 400。

本地 SQLite 新增 `shift_reconciliations`，逐批保存检查点，修订比较更新防止旧执行覆盖新结果。停止或认证失败后保留同一报告，续查不重新选择来源。继承工作台单作业限制、来源校验、凭据隔离与固定错误输出。

## 验收

- 类型与脚本语法通过；12 项定向测试通过，包括新增 5 项对账语义、1 项 HTTP 完整链路及 6 项工作台回归。
- 相同队列总数但任务替换，仍能识别各一项新进入和离开。离开但 pending 单列；503 失败保留，重开后只重试失败项；403 中止后续批次；预取消不发请求；旧执行保存被拒绝；缺定位不猜接口。
- HTTP 验证创建 → 未完整报告读取 → 原报告续查 → 完整 → 幂等读取/历史；反序班次、缺失来源正确拒绝。
- 真实浏览器以本地班次 1/2 生成对账 **1**：继续积压 211，新进入 0，离开 0。此结果不宣称任何处理收益。
- 工作台重启后读回对账 1；页面反序选择正确报错，“继续积压”筛选和 21—40 / 211 分页通过。
- 隔离内存库回放“一个真实旧任务离队”的假设，再用真实本地运营 API 回查原任务：`decided=0, stillPending=1, unconfirmed=0`。未修改共享审核队列；此证据验证原接口兼容与错误归因，不能称真实离队验收。

## 未完成约束与退出条件

本包退出条件是来源可比较、变化可逐项核对、失败可续查、历史可重开，且页面有明确结果和错误反馈。

P1：老扫描缺失原定位时保留未确认，重新扫描能改善后续报告，但无法凭空补全旧报告。退出条件是由已有运营详情提供可核验原定位后另行设计显式补录；此前禁止猜测或标记完成。

P2：审批结果与读者访问结果有不同语义，本包不提供处理率或自动归因。只有确定需要评估读者效果、并明确隐藏/展示版限制等影响的口径后，再开单独业务包。
