# 开发方向与进度批判性评审 · 2026-10-30

评审身份：教师视角。评审依据：`business-first`（六条 demo 化信号 + 克制条款 + 自问三句）、[业务共识](../../项目业务共识.html)、[当前进度](current-progress.md)、A/B 阶段复盘、实际代码与迁移。

## 一句话结论

**方向没有整体跑偏，但主航道跑偏了：工程可靠性被做成了主线，需求验证被推成了支线。**

项目已经交出的东西，比绝大多数同类项目扎实；问题不在于"做得差"，而在于"把最贵的能力用在了最不该优先的地方"。当前仍可纠正，若继续按 B3 → C 的顺序推进，结构性失衡会变成路线错误。

## 一、没有跑偏的部分（应当保留）

1. **交付的是纵向切片，不是空壳。** A 阶段从收码登录到草稿保存、冲突另存、离机备份、跨机恢复都有真实证据，接口不是先注册占位再补实现。
2. **失败与并发被当真处理了。** `mutation_id` 幂等、基础修订校验、冲突另存、`state_revision` 乐观并发、管理动作事务回滚注入测试，这些都是"能承接真实业务"的写法，命中 business-first 的正面标准。
3. **契约与权限没有糊弄。** OpenAPI 是唯一契约，运行时有请求/响应校验，匿名 SSR 与作者接口共用同一访问判定，未授权读取统一不可访问。
4. **范围克制在基础设施上成立。** 没有为了"显得先进"上 Redis、独立 MQ、微服务或 Kubernetes，备份与告警用的是现成能力。
5. **证据分级诚实。** 主动区分浏览器夹具、真实 MySQL、真机、外部服务、跨机恢复，不互相冒充。这是稀缺品质，也是项目最大的资产。

这些工作不是浪费，它们降低了后续返工成本。问题只在**顺序**。

## 二、跑偏的部分（按严重度）

### 1. 严重：在零读者阶段做"成熟平台"的版本治理

B2 交付了 V1/V2 连续版本、读者时间线、历史阅读开关、展示指针切换、隐藏恢复、状态号并发控制。这套能力对应的是**已有读者、评论和作者规模**的平台问题。当前事实是：0 个外部读者、0 条评论、1 位作者（开发者本人）。

- 证据：作品管理相关 9 个接口、2 个迁移、独立 `/my-works` 页面；互动与发现接口为 0。
- 命中：克制条款"为想象中的未来场景提前引入抽象层"。
- 代价：版本时间线、历史权限、展示切换一旦公开，就是长期维护承诺（每个读取入口都要叠加权限判定），而它现在换不来任何一条真实反馈。

### 2. 严重：治理被提前规格化成重型状态机

B3 清单包含：观察期 7 天状态机、灌水规则与阈值、自动临时限制、48 小时积压告警、站内复核、待审替换/撤回、版本级/作品级/账号级三级处置。文档同时承认"具体规则与阈值尚待评审"——**规则本身是假设出来的**。

- 命中：六信号之"数据是假设出来的"。
- 更麻烦的是它形成了死循环：治理不完成 → B 不算完成 → 不敢开放 → 永远没有真实违规样本 → 规则只能继续靠想象定义。
- 正确顺序应是：先有最小人工处置入口（限制、撤销、留痕），跑出真实样本，再决定要不要状态机。

### 3. 严重：验证主体是开发者本人，验收没有门禁作用

A 的验收写的是"用户本人确认"，A 的两项真机尾项（粘贴、Wi-Fi/蜂窝切换）被搁置后，项目继续推进 B1/B2。B 的验收同样是"用户本人回复操作正常"。

- 这使验收从"门禁"退化为"记录"：不通过也能继续，尾项可以被无限搁置。
- 命中：六信号之"写完即结束——不验证真实场景"，以及自问第一句"明天接入真实用户，第一个坏掉的地方在哪"。
- 客观补充：项目自己已经承认"验收参与者主要是开发者本人"，说明团队知道问题，但行为没有改变。

### 4. 严重：公开门槛被当成后置条件，导致所有"真实环境验收"仍是自测

域名实名/备案/DNS/公众 HTTPS、自有发信域名、主机外探针，是**唯一能让真实用户走进来的开关**（按 2026-10-30 决策暂搁置，见第四节的决策记录）。它们至今未完成，Resend 仍只能给本人邮箱发码。于是：

- ECS 上的"真实环境"只有开发者一人；
- B1/B2 只在本机通过，用户不可感知；
- 对外可感知能力约等于 A 阶段，与文档宣称的"B1/B2 已交付"相差两个增量。

这是当前"进度"判断的关键：**以用户能拿到的价值计量，项目仍在 A；以工程完成度计量，项目已到 B2。两张进度表相差约两个阶段。**

### 5. 中等：文档密度已经高于产品密度

215KB 文档 + 58KB 规格 HTML + 12 篇复盘，对应 3111 行后端与 2523 行前端；6 次提交里，文档与验收记录占比很高。

- 流程纪律本身是资产，AGENTS.md 的"接口交付含契约与失败场景"也应保留。
- 但已经出现"用复盘证明进展"的替代效应：复盘写得越完整，越容易让人误以为业务被验证过。
- 命中：克制条款的变体——以业务严谨为名扩大流程范围。

### 附带发现（不属于方向问题，但应修）

首页对用户写"公开发布与内容发现正在开发中"，而 B1/B2 已在内部宣布交付。对外口径应按"用户能否使用"而非"代码是否合并"表述，否则内部进度感会持续失真。

## 四、纠正处方

### 决策记录：域名与备案搁置（2026-10-30）

项目负责人决定**先将域名与备案的优先级搁置**，本报告原 P0 中的相关内容据此调整。搁置不等于门槛消失，只表示当前不投入。

- 搁置项：域名实名、ICP 备案、公网 HTTPS、Resend 自有发信域名、主机外探针。
- 直接后果：外部作者收不到验证码，**外部用户验收当前不可执行**；所有验收只能算技术验证，不能用于判断社区价值或用户留存。
- 恢复触发点（命中任一即把域名/备案拉回 P0）：启动校园招募或任何外部测试；连续两个增量未接触开发者以外的人；B3 治理规则需要真实违规样本才能继续。

### P0：在私有入口完成部署，不降低安全边界

1. 把已完成的 B1/B2 部署到现有杭州 ECS，通过 SSH 隧道访问，不新购服务器。
2. 保持 `COOKIE_SECURE=true`、同源保护与 `API_ENABLE_DOCS=false`；不接受以 IP 直连 + HTTP 换取"能打开"。
3. 退出条件：开发者本人在真实 ECS 上完成一次发布与一次匿名阅读；结论标注为"私有环境技术验证"，不冒充外部用户验收。

### P0：冻结 B3 工程实现，只保留最小人工治理

1. 只做：限制版本/作品、撤销、原因与留痕、最小复核记录。
2. 删除/推迟：7 天观察期状态机、灌水规则与阈值、自动临时限制、48 小时告警。
3. 退出条件：积累至少 3 个真实违规或误判样本后，再评审规则与时效。

### P1：把"发现 + 反馈"插到版本时间线之前

1. 最小闭环：标签/风格浏览页、作品列表、单层评论、读过与收藏、站内通知。
2. 暂停对外暴露版本时间线 UI 与历史阅读开关（后端能力保留，不拆）。
3. 理由：反馈是验证"内容是否值得读、社区能否成立"的唯一手段，也是 C 的核心；没有它，B 做得再完整也无法回答业务问题。

### P1：验收口径调整为"私有 + 白名单"，外部样本标记为阻塞

- 当前对象：开发者本人及可当面协助的白名单账号；只验技术正确性。
- 外部样本（3–5 名外部作者、约 10 名读者）**阻塞于域名/备案搁置**，从阶段完成条件中移除，不得当作已通过或悄悄降级。
- 指标保留但暂不采集：独立完成发布率、读完率、7 日回访、评论率、发布失败率。
- 规则：域名/备案恢复优先级后，外部样本验收立即重新生效；未达样本量不得宣布阶段完成。

### P2：降低文档成本

- 复盘只写三件事：决策变更、证据、未决项；单篇控制在 500 字内。
- 新增接口不再单独写长文复盘，并入契约与阶段记录。
- 保留 AGENTS.md 的契约与失败场景要求，删除重复叙述。

### 刹车指标（建议写入 AGENTS.md）

出现任一条，立即停止功能开发，转向用户验证：

1. 命中域名/备案恢复触发点（出现外部测试需求、连续两个增量无外部接触、治理需要真实样本）；
2. 新增代码超过 50% 落在治理、版本或运维；
3. "待评审"事项超过 10 条仍未决；
4. 文档增量持续大于代码增量。

## 五、给项目负责人的三句话

1. 你已经证明了自己能写出可信的保存与恢复系统；现在要证明的是**有人愿意读、愿意回**。
2. B3 不是业务，是制度；制度没有真实样本时写出来的每一行，都是未来的返工。
3. 判断是否跑偏只需要一个问题：**这一周新增的东西，有没有让一个陌生人更可能读到一篇作品并留下反馈？** 如果答案连续几次都是"没有"，就是跑偏了。
