# Tako 发布诊断评测复盘

项目目标是用一个真实的 Tako 业务问题练习任务定义、失败归因、改进与复测。发布诊断仍适合这个目标。现有代码能用真实接口核对业务规则，也能保存并复查模型错误。后续开发把过多精力放在交付补救、费用恢复与源码复验，直到这几项收口仍缺少一组可以支持产品取舍的对照结果。

## 本次离线复核

在 Node 24 下直接使用现有合成环境、`evaluate` 和 `deliver` 复现。四项检查都只调用本地函数与受控 transport。

| 发现 | 复现与影响 | 开跑前处理 |
| --- | --- | --- |
| **P1 · 同一夹具的工具结果矛盾** | `display-limited` 与 `display-pagination` 的 `find_my_works({query:''})` 返回 `display_limited=false`。同一状态下的版本查询在找到 V1 后返回 `true`。目录把字段写死了，真实目录 SQL 从展示版本读取。不同查询路径会遇到不同事实。原批次这两例仅走版本查询，因此现有轨迹无法归因到这个错误。 | 目录和版本页从同一夹具状态生成。用固定状态下的两条路径确认字段一致。对故意注入的变化另设任务并标记时间线。 |
| **P1 · 取到证据与答到问题分离** | `draft-ahead` 使用参考解的证据和标签，把文字改成“已发布，请去详情查看”，`automatic_passed` 仍为 `true`。回答省略 R2/R1 比较。原评分器明确要求人工复核，这个反例说明机器通过一列的覆盖范围。 | 业务完成判定增加对用户实际收到的信息的复核。保留机器检查与人工判定两列，收录这份反例，校准前后沿用相同标准。 |
| **P2 · 有效替代取证路径待校准** | `work-limited` 的本人目录已给出匹配作品 ID、作品级限制和展示版本。与原发布回执一起引用时，v3 仍报 `unsupported_access_claim` 和 `missing_goal_evidence:state`，因为只接受时间线工具。 | 区分目录摘要足以支持的事实与确实需要状态修订的操作。把必要的快照要求写进任务，按事实与前提评分。 |
| **P2 · 补救依赖原提案触发条件** | 对 `older-display` 固定同一份正确证据。正确提案放行并完成目标，错误限制提案经程序修正也完成目标，原提案写 `unknown` 则放行但未完成目标。分歧来自交付策略的分支。 | 报告分列取证、原提案、程序补救与交付结果。比较 Agent 方案时固定交付策略和评分版本，避免把补救分支差异计成模型变化。 |

## 下一阶段只完成一次业务对照

**问题是作者给出不同程度的信息时，动态工具选择能否比确定查询更好地完成发布核对。** 把已知标识和需澄清两类分开计数。单独看总体分数会掩盖固定查询足以解决的场景和 Agent 可能有价值的场景。

1. 修正夹具一致性，先用原 11 例做开发回归。你独立复核 3～5 个有分歧的样例，先写必须传达的事实、允许下一步及禁忌，再看答案。优先选版本比较、先审受理和同名澄清。保留两份原判定和解决分歧的理由。
2. 建一个正常可用的确定查询基线。按同样可得的标识读取原回执和作品状态，必要时分页或要求用户明确对象。两边使用相同输入、会话、工具权限、夹具、读调用上限及共同交付边界。基线从用户输入和查询结果决策，参考解仅供评测。跑通一个澄清后补标识的分支和一个用户无法补充的分支。
3. 基线与当前 Agent 先在开发集对照。记录每次事实正确性、应答完整性、动作可执行性、澄清/未确认、工具调用数、耗时与模型费用，原提案和程序补救另列。只从实测失败选一项可解释改动。涉及 Agent 前后比较时固定工具、评分器和交付策略，只改变选中的因素。
4. 在选择改动前固定验证协议，并保留 6～8 个独立于开发样例的留出场景，按不同状态组合和用户交互分支选取。冻结版本后用同场景配对跑，小样本每例目标 3 次，报告逐例成功次数和全部重复都通过的例数，保留未完成与未执行项。保守模型费用仍沿现有上限，遇不明费用按账本规则停。合成实验的用量和时延标明环境，真实服务另作可用性验证。

交付物是一张逐例对照表、一份失败归因记录和一个业务决策。已知标识的确定查询达标且成本更低时，推荐作为该场景默认。只有实测能稳定改善澄清或动态取证的场景才有理由保留 Agent。这个阶段冻结账本、源码归档、交付补救扩展、新业务工具和产品接入。退出条件是能用原始证据解释选择，并让你讲清亲自负责的判定与取舍。
