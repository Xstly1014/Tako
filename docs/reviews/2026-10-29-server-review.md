## 结论

当前是增量 A 的服务端阶段，不是可运营首版，也不是已完成的增量 A。先前实现推进过快，契约、可观测性及规格差异收口不足，有 demo 化倾向；部分并发与权限验证已经真实存在，不应一概否定。

## 本轮纠正

| 问题 | 修正与证据 |
|---|---|
| 只有手工 Markdown 接口说明 | 引入唯一 OpenAPI 3.0.3 契约源，启动校验，提供 JSON 和本地 Swagger UI |
| 文档可能与路由脱节 | 双向路由覆盖测试：实现无文档、文档无实现都会失败 |
| 文档只展示快乐路径 | 写明 Cookie、来源、验证码失效、冲突、去重、超时重试及错误分支 |
| 输入可能偏离约定 | 运行时执行契约校验，拒绝未知字段、null 类型错误、无效 UTF-8、多个 JSON 值及过大请求 |
| 没有请求关联 | 响应 X-Request-ID、错误 request_id 与脱敏结构化日志关联 |
| 创建请求带无意义零值字段 | 不再序列化创建不需要的 draft_id 和 base_revision |
| 校验测试自身可能虚假通过 | 用缺字段与未声明状态码的故意错误响应确认校验器能检测漂移 |

Swagger UI 固定 5.34.0，资源与许可证随仓库保存，不依赖运行时外部 CDN。OpenAPI 校验采用 kin-openapi v0.151.0；查阅官方安全信息后撤回最初选择的旧版。

## 可以主张的能力

- MySQL 事务级草稿幂等、修订冲突防覆盖、跨账号隔离和恢复副本去重，已有真实数据库集成测试。
- 验证码一次性消费、会话撤销及 HTTP 登录到保存已有测试；邮件使用测试替身，不能主张真实送达。
- HTTP 契约加载与路由覆盖、响应检查及其反例测试、关键非法输入拒绝已有自动检查。
- 正文、认证信息和输入值不进入访问日志；日志记录路由模板，不记录原始 URL/query。

## 自我纠偏

1. 不再以“测试通过”笼统替代“哪种条件下哪些场景通过”。
2. 增加接口必须同步契约，不等用户提醒。
3. 阶段复盘在纵向链路结束、范围改变和验收前执行；发现承诺差异立即记录并收口，不增加无关中台。
4. 下一项优先修复发送链路的已知规格差异，再进入新的业务扩展。

## 本轮验证结果

- 本机 `go test -race -count=1 ./...` 与 `go vet ./...` 通过，数据库为真实 MySQL 8.4。
- 网关下 `/docs/`、Swagger JS/CSS 与 `/openapi.json` 实测可访问，契约为 OpenAPI 3.0.3。
- 错误 null 输入返回 400，响应头、错误体和结构化日志的 request_id 一致。
- 构建替换期间第一次探测出现短暂 502，服务稳定后复核通过。当前单实例无无中断发布保证；上线部署方案仍需处理就绪检查与网关切换。
- GitHub Actions 仅完成配置，尚未推送或运行；没有真实 SMTP、浏览器登录及恢复演练验收结果。
