# C2 · 失败恢复与旧成功结果隔离

2026-11-02。并行端维护。起点 `codex/mobile-publication@402a8aa`，本次 fetch 的主开发 main 仍为 42bc325；对方没有新发布提交不代表没有进行中工作。本端继续既有 C2 的正确性修复，没有接管 C1/auth 或增加新业务。

## 确定缺陷与影响

原 `flow.ts` 的 restore 在 GET 原预览之前先改 pendingPublish，只有 GET 成功才替换 preview/result。触发顺序：旧页面 A 已显示成功；同账号页面 B 确认旧结果后开始另一发布并丢响应，安全项现存 B 的未知请求；A 主动读取保留记录时 GET B 失败。A 此时将旧成功结果 A 与请求 B 混在同一状态中，reset 判断存在 result 而允许确认，标识又与 B 相符，于是删除了 B 的未知 journal。

这是本端代码的 P1 正确性缺陷：会丢失用户已授权保留的最小确认标识，并可能把旧成功显示成新结果。复现没有删除草稿或服务器正式版本，也没有跨账号泄漏证据，不能扩大成正文丢失或越权事件。

新增真实 PublicationFlow 双实例回归在修复前失败（68 项模型中 67 通过、1 失败，诊断指向 publications.test.ts 的新用例），失败为本应拒绝的 reset 竟然成功；修复后通过。失败过程没有通过跳过或修改权利绕过。

## 修复行为

- 恢复先在局部变量中读取和校验目标；请求/快照/结果一同替换，失败不会把新请求配到旧成功上。
- 恢复未完成或失败时保持 recoveryBlocked；reset 和 publish 都拒绝，实际页面隐藏旧成功/快照与确认入口，只提供明确读取重试。未读取成功之前，旧结果不能授权清除新记录。
- 只有明确服务器 410 preview_expired 才进入过期清理，并在写互斥内比较被读取的原 mutation_id。安全项已换成另一请求时保留记录、保持保护并提示先恢复；不会因旧请求过期而解除新请求的保护。
- 成功恢复仍只 GET；未消费请求需要再次主动检查，已消费请求展示对应结果。未增加自动 POST，不保存正文或表单，不改变账号/最小标识策略。
