## 人工校准与失败归因

- 作者要求核对具体修订时，用户确认必须说清服务端工作稿 R2 和原发行源 R1，同时说明保存的业务含义。缺任一修订号，人工“回答了问题”项失败，即使事实检查通过。两边实测答复均通过此项。
- 先审必须说明已取得历史受理回执、尚不能确认正式发行以及当前审核状态未知。下一步可以查同一提交记录。不得把回执时间的状态外推到现在。
- 同名作品先说明无法唯一确定、请求补标识；补充后只核对选中的作品。无法补充时，保留未知，不猜候选。若解释与实际导航对象冲突，人工判定失败。
- 用户确认，明确指出限制发生在当前展示版本，即满足本例的范围区分要求，可以省略作品层未受限。两边在此项的人工完整性均通过。若作者另问作品层是否受限，仍需回答该问题。本条只校准完整性分项，表中总分仍为机器检查。

同名失败可分三步。第一轮模型用目录摘要提出 `unconfirmed` 与 `no_recorded_block`，无原预览证据也无已确认的作品，门禁拦截后给出通用澄清。第二轮已正确取到所选作品，但模型建议核对未提供的原预览，程序补救改回作品详情。旧模板只看到“有多个候选”，仍输出“尚未明确具体作品”。此次只修这个可重现的模板条件，升级交付版本到 v3。用原提案和原证据重放，第二轮矛盾消失，第一轮失败仍保留，未重新调用模型。新增回归验证选中作品的标识与状态仍绑定。

## 留出验证协议

开发集结果只用于找错。留出实验按两类分别计数，先登记输入、合成状态和人工判定，再固定两个方案的源码、共用门禁、模型配置与单轮调用上限。每例各跑 3 次，分别报告逐次成功及 3 次全成功。运行失败保留原位，业务失败不触发重试。评审以最终文字、目标对象和实际下一步为准，先人工判读再看机器结果。六个独立输入、初始状态和逐轮人工判据见 [冻结用例](../../agents/author-support/src/holdout.ts)。

| 分组 | 场景 | 成功判据 |
| --- | --- | --- |
| 标识齐全 | 原 V3 正式发行，最新 V4，仍展示 V2 | 三者对应正确，解释最新正式版与当前展示可不同。 |
| 标识齐全 | 原预览受理，同时当前另有正式展示版 | 历史受理仅对应原请求，区分现有公开版本与原请求结论。 |
| 标识齐全 | 原预览成功，给出的作品标识属于另一作品 | 不合并两个对象的状态，要求核对标识。 |
| 需补充 | 同名首轮查得两件，作者补的是第二件作品标识 | 只核对第二件，其可见状态与第一件不同。 |
| 需补充 | 作者只有标题，澄清后仅拿到原预览标识 | 从原回执绑定作品，继续核对对应版本及访问状态。 |
| 需补充 | 澄清后作者给出无法读取的标识 | 说清无法读取，保持未知，给出核对原标识的只读下一步。 |

退出条件：冻结并完成留出，保留人工分歧，按场景比较完成率、错误主张、耗时和费用。当前开发样例支持优先考虑固定流程。只有 Agent 在某类留出任务上出现可重复的新增完成，同时无严重越权或误导，才考虑在该类保留。上线前的真实接口验收独立于此次比较。
