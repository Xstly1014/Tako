# 项目业务盘点与本端下一步 · 2026-11-02

## 核对范围与结论

本轮已重新 fetch。远程 main 仍为 `3a17e22`；本端作者管理分支为 `332b21b`，包含此前 CI 成果，尚未合入 main。工作区核对前干净。依据最新源码、OpenAPI、C1/M1 规格及阶段复盘盘点；本轮是规划评审，没有重跑工程测试、构建或设备验收。

当前最值得推进的业务是：作者在 App 写一篇中篇，明确保存并发布，读者发现/阅读/反馈，作者回来修订和管理。Web/API 已有这条链路的主要能力；App 读者侧和本端作者管理已有源码及分层工程证据，App 私密草稿与正式发布尚未形成完整入口。不能将原型、生成类型中的接口、分支代码或 CI 通过算成用户手机可完成这条链路。

## 需要争论而非默认接受的判断

1. **把短内容和长文齐备作为所有对外验证的前置，会推迟真实反馈。** README 保留“正式首发需短内容/长篇基础能力”的口径。本端建议在不改变三频道长期方向的前提下，另定义“中篇 App 小规模私测”里程碑，先验证写作到反馈。该建议不代表用户已经调整正式首发范围，不能据此删除既有方向或擅自公开上线。
2. **当前更缺可完成的作者路径，功能数量已不足以代表进度。** 下一阶段应考核一篇真实中篇能否从写作走到读者反馈，而不是增加按钮、测试条数或维护功能。点赞、关注、推荐、复杂治理参数先不扩张。
3. **已推送独立分支仍有集成债。** CI 和 M1 没有进入 main，入口报告又保留“CI 未认领”等旧状态。主开发集成时须统一当前账本，并将历史记录明确标为快照；本端不同时重写同事负责的入口文档，也不擅自推 main。
4. **设备验收可以暂缺，不能持续被工程成功覆盖。** 设备不可用期间继续独立开发；下一轮可安装包前冻结源码并构建，真实移动作者交付前补生命周期/输入/返回。若长期无设备，应讨论测试条件与交付目标，不能不断增加“已实现但未体验”的功能。
5. **没有真实运营结果，不能靠合成规模补齐。** 验证重点是作者是否完成保存/发布、读者是否读到目标作品并愿意反馈、作者是否回访续写；合成数据、分页正确与压力容量是不同证据，不用虚构活跃度或增长指标代替。

## 本端下一步建议：App 固定预览与正式发布

这是 C1 后续能力的并行分工建议，不冒充已实现或已与同事约定独占。实现前先确认以下文件与交接边界；M1 的授权不自动替代 C2 文件归属确认。

### 分工与接口

- 同事继续 C1 的加密存储、自动保存/同步、冲突副本、草稿列表和编辑页、会话/退出适配。
- 本端建议负责新的发布客户端、固定快照/待确认请求状态、发布预览/确认页、模型/真实 API/组件测试及阶段复盘。建议独立文件为 `mobile/src/api/publications.ts`、`mobile/src/publication/**`、`mobile/src/app/publish.tsx`、`scripts/mobile-publication-ui/**`；实际路径确认后再编码，不占用 C1 实现文件。
- C1 向发布页提供本人草稿 ID 与**已获服务器确认的修订号**，同事负责编辑页“去发布”导航。只有本机暂存或同步未知时不能将内存正文标成服务端保存；发布页不从本机存储绕过 C1 读取私稿，不写回工作稿。
- 后端只复用 `POST /api/publication-previews`、`GET /api/publication-previews/{id}`、`POST /api/publications`，以 OpenAPI 为准。不先修改后端/生成声明来迁就 UI。

### 交付顺序与退出条件

| 顺序 | 本端交付 | 必须验证的退出条件 |
|---|---|---|
| 1 | 对齐已确认规则与 C1 交接，再完成发布客户端/状态逻辑 | 固定修订、原请求幂等、账号/作品身份校验、明确失败与未知结果、过期预览均有失败证据；基础类不计完整发布交付 |
| 2 | 接入明确可达的预览/确认页 | 用户填写简介/平台标签并主动确认原创或授权；完整显示快照，草稿后来改变不能偷偷换正文；缺笔名、未同步、版本冲突、过期各有可继续路径 |
| 3 | 正式发布与发布后导航 | 首发绑定唯一作品，修订追加版本；未知结果沿原请求确认，不重复发布；隐藏作品发布后仍隐藏；平台限制/不支持的审核状态不能被客户端绕过。成功去阅读或作品管理时重新检查现状 |
| 4 | 与 C1/M1 集成及移动交付收口 | 一篇中篇在 App 完成新建/续写、服务器确认、固定预览、正式发布、发现/阅读/评论、作者管理与修订；分层检查通过，冻结源码构建并核对包，设备恢复后完成真机门槛 |

预览有效 24 小时，待提交快照与正式版本不可混淆。原请求恢复策略沿既有身份和数据保留权利另行核对；不能在规划阶段擅自新增磁盘正文缓存、自动补发或发布权利。涉及未确认的数据丢失/跨账号行为立即提出讨论，常规实现自主推进。

## 优先级与协作约束

- **当前开发 P1**：同事 C1，本端完成 M1 集成交接并落实上述 C2 最小分工，然后推进发布入口。两端共享契约和业务错误语义，避免各做一套草稿保存或认证。
- **移动交付前 P0**：真实设备账号/存储/键盘/返回/后台与进程终止、跨账号、冲突及发布重试验收。C1 原生存储失败不能只靠 HTTP 预检代替。
- **合并及对外评审 P1**：前端依赖审计明确负责人并修复验证；分支成果进入集成版本，更新统一入口账本；新 APK 未构建前不声称本轮包已可安装。
- **公开测试前单独评审**：访问入口/HTTPS、实际运营处理人、账号生命周期、备份恢复及通知边界。当前不连接 ECS、不购资源、不发对外通知。B3.2 暂停状态不因本报告自动改变。
- 每次阶段推送前先拉取远程 main、阅读同事最新报告；有共享改动先合并并重跑受影响检查。只推本端分支，不强推、不同时修改同事 C1 或共享依赖。

本报告是当前业务与证据盘点，以及下一步建议；不新增已确认业务权利，不将未来发布页面或对外私测写成已完成。
