# 增量 B · 从规格进入实现

2026-10-30。前端视觉暂停打磨，不视为定稿。主要行为已明确，但详细技术设计和部分治理参数仍待评审。本计划不改变已确认范围，不表示 B 已实现或已验收。

## 下一步：第一条纵向链路的技术评审

目标：原账号选择固定已保存草稿修订，确认标题/正文/简介/标签及授权声明，提交后以稳定作品链接匿名阅读；保留最新工作稿，发布重试不重复。未具备治理能力前只在私有测试环境验证，不对外开放创作。

先交付技术设计与状态/并发矩阵，再落正式 OpenAPI、迁移和实现。不能先把整套接口注册为空壳，或在运行时返回伪造成功占位。

模型职责建议：作品保存稳定身份和关联工作稿；固定提交保存作者明确确认的内容；正式版本保存不可变完整信息及连续编号；展示版本/作者隐藏/历史阅读/平台限制/账号审核策略分开管理；审核待办与版本或提交固定绑定。表数量、字段和索引需结合现有代码细化，不在此强行冻结。

必须解决的技术问题：

- 固定预览所引用正文如何可靠保留、何时过期；不能被 A 的快照清理提前删除。期限涉及数据保留权利，技术设计需明确提出方案，未确认前不能任意清理。
- 发布、作品绑定、版本编号、幂等结果与后审待办的原子提交；失败不能留下“已发布但没有后审任务”的半成品。
- 提交时重新校验账号观察期与资源归属；不信任预览页面曾看到的账号状态。并发策略以事务提交的顺序建立清晰语义。
- 同一草稿多设备首次发布只绑定同一作品；不同请求如何避免意外重复正式版本，须在契约中明确，不能只靠按钮禁用。
- 作者切换展示、隐藏和平台限制发生后，读者入口、版本入口和分享信息采用一致访问判定，不把全部版本返回给浏览器再隐藏。
- A 原有草稿、历史恢复和幂等保存继续可用；迁移与备份覆盖新增 B 数据，不以测试清空用户库。

## 分段实施与验收

1. B1：固定内容预览、作品绑定、正式发布、稳定链接匿名阅读。先覆盖正常作者的私有测试链路，观察期作者不得绕过待审流程；该流程未实现前明确拒绝不支持操作，不假装正常放行。
2. B2：版本时间线、历史权限、展示切换、隐藏恢复。验证受限版本不进入读者时间线；所有读取接口共同执行权限。
3. B3：先后审、替换/撤回、限制及撤销、七天观察期、48 小时目标与站内最小复核。明确规则获评审后才启用自动临时限制；不接大模型。
4. B 整体验收：真实 MySQL 并发/迁移/契约测试、前端状态与浏览器验证、私有 ECS 更新和恢复演练。各段可部署私有测试，但任何一段不能冒充 B 整体完成或公众上线。

每段实际交付包括实现、契约、必要反例测试和阶段复盘，不以文档代替接口，也不等所有后端完工才接前端。

## 决策分工与范围控制

常规 SQL、包结构、事务锁顺序、索引和错误码由开发者提出并验证，不逐项要求用户批准。涉及作者内容保留、自动限制阈值、待审释放和复核终结等业务权利，继续共同评审。不存在一个含混的 published 状态包办审核/隐藏/平台限制。

尚未冻结的治理参数可以晚于 B1 细化，但必须先于相应能力启用和 B 整体验收。审核/复核积压不自动放行、不自动判违规。前端视觉优化另记，不作为业务流程已经通过的依据。
