# 从参与评测到面试讲清楚

这是参与计划，不是已经完成的个人经历。当前事实以 [阶段复盘](../reviews/author-agent-initial-review.md) 为准：一个真实模型开发任务，尚无整体准确率、盲测成绩或改进收益。

## 你需要亲自负责的工作

第一周安排三个各约一小时的参与时段。每次留下一份自己写的判定或实验记录；不要求先通读仓库，也不要求独自重写整个框架。

### 第一次：先于模型定义“答对”

先不看模型答案，自己处理下面的作者咨询：

> 我刚发了修订版，页面没显示结果，朋友也打不开。要不要再发布一次？

已知服务器事实：原预览有 V2 的发布回执，作品当前展示 V1，作者隐藏为 true。

用自己的话写三项：哪些事情确定、哪些事情不能确定、作者下一步应做什么。再独立判断三个变体：

- 原预览查询超时，其他状态不变。
- 原结果是先审受理，正式版本为 0，没有正式发布时间。
- 原预览确有 V2 回执，但属于另一件作品。

每题写“必须说什么、不能说什么、需要什么证据”。之后再与实现比对。你在负责业务验收标准，不能让提示词或模型答案倒过来定义正确性。

### 第二次：审查评分器，而非只看绿灯

先读 `agents/author-support/tests/grade.test.ts`，再读 `src/grade.ts`，最后读 `scripts/live-probe.ts` 中案例目标检查的部分。尝试回答：

1. 为什么同一作品的其他预览回执也可能用错？
2. 一直说 unknown，能否通过证据检查？为何这不等于解决了问题？
3. JSON 结论正确，但 explanation 建议重复发布，当前程序会不会漏判？

第三题是当前能力边界：程序未做完整的自然语言语义检查，需人工复核。请自己写一个这样的矛盾答案，运行现有评分器观察结果，再判断需要补程序规则、人工判定还是未来的模型评审。不要修改生产规则让错误答案获得通过。

从根目录执行以下命令，不调用付费模型，也不改共享业务数据：

```powershell
npm run test --prefix agents/author-support
```

交付一条自己的评分反例及最小修正建议。若决定修改，放到新测试中再改评分器，分别记录修改前后，不覆盖已有真实试验报告。

### 第三次：读一份实际轨迹并做人工标注

阅读本机 `.runtime/author-agent/runs/dc373773-7423-4a12-995b-9403da1ece16/` 下的 `report.json` 与 `review.json`。本次只有合成数据，不是用户工单。

把“用户问题 → 模型选择的工具 → 工具能证明的事实 → 最终回答 → 程序判定 → 自己的人工判定”画在纸上或写成六行。给每个主张注明依据，圈出程序没覆盖的内容。不要把轨迹摘要误当成完整可重放输入；目前未保存全部脱敏工具投影，这是下一阶段待补项。

这次实际过程是两个模型请求、两次工具调用，不是两条评测案例。12项真实接口检查和14项程序测试也不能计入模型成功率。能够解释这些分母，是讲清评测结果的基础。

## 随后两周亲自完成一个小闭环

从上述变体中选择一类，负责三至五个案例的业务标准和人工判定。先写标准，再执行；有失败时先复现并定位，再一次只改变一个因素，使用同一组任务比较。不要用改过规则的结果覆盖原结果。

记录表可直接复制：

```text
问题与来源：现有哪条业务规则/哪次实际现象？
初始状态：账号、目标资源关系、工作稿/正式/展示/审核状态。
任务目标：哪些事实必须查明，哪些信息不足必须说明？
禁止行为：哪些建议或数据访问超出权利？
运行版本：代码、策略、模型返回标识、夹具与评分器。
实际输出：结构化结论、证据、自然语言建议。
程序判定 / 我的判定：各自依据是什么，是否有分歧？
归因：模型选择、工具投影、业务规则、评分器或环境哪层有证据？
修正与复验：改了什么，原案例和相邻案例发生什么变化？
尚不支持的结论：样本数、重复次数、场景或留出集不足在哪里？
```

受控注入超时叫故障试验；自然运行观察到的错误叫实际失败，两者都值得分析，但不能混称。若所有案例通过，就报告覆盖与未覆盖，继续找边界，不编造提升幅度。

## 面试叙述的结构

先讲两分钟，再让面试官选方向追问：

> Tako 作者会遇到“没看到提交结果，朋友又打不开”的情况。这可能是已经发布但隐藏，也可能只是先审受理。我在现有业务上做了只读诊断 Agent，重点验证它是否根据正确对象和状态给建议，避免误导作者重复提交。工具调用成功不等于回答正确，所以我把事实与证据检查、案例目标和人工复核分开。当前处在初期验证，接下来通过可重复案例分析失败。

这段只描述项目现状。亲自完成上面的闭环后，再补“我定义了哪些标准、发现什么具体问题、为什么选择这项修正、复验有什么证据”。没有做过的部分，用“项目实现了/我正在学习验证”，不要背成自己独立完成的工作。

准备回答六个追问：

- 为什么需要 Agent，固定表单或规则查询在哪些地方已够用？当前只验证开放式咨询的价值，尚无线上效率收益证据。
- 为什么四个工具够起步？工具数量由诊断事实决定，复杂性来自状态组合、权限和失败语义。
- 怎么知道答案正确？业务参考事实来自受控初始状态与授权服务，而不是另一个模型随口给分。
- 为什么不用固定工具顺序评分？不同有效查询路径可能支持同一正确结论。
- 什么是目前最具体的工程发现？新先审流程让原 published 字段可以表示受理，必须与正式发行分开；这是接口语义适配风险，并非已观察到的模型误答。
- 目前有多可靠？只完成一个真实模型开发任务，不能推断整体成功率；明确说明下一阶段如何补证据。

## 简历更新门槛

当前可写：只读工具、业务证据评分、反例验证、首个真实诊断任务、用量与预算控制。暂不写：完整评测平台、生产客服上线、真实工单规模、准确率提升或节约人力。

下一次有完整案例与复验闭环后，用一条“具体业务错误 → 定位 → 修正 → 复验结果”替换简历里的起步验证描述。只有获得可靠分母、版本与重复结果后再加入量化指标；简历保留业务问题与成果，技术实现留给追问。
