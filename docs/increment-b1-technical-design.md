# B1 技术设计 · 固定预览、发布与稳定阅读

2026-10-30。状态：B1 已按本稿进入实现，正式契约版本 0.4.0、新增迁移 00007；完整 B 仍未完成。依据 [B 业务评审](increment-b-review.md) 与 [实施计划](increment-b-implementation-plan.md)。用户再次确认可发布预览中的旧修订。未提交预览的 24 小时有效期与过期正文清理已由用户明确确认，已提交内容不受影响。

## 1. 本段承诺与运行边界

原账号从确定的已保存修订准备发布，检查完整信息，明确确认后生成正式版本和后审待办，通过稳定链接匿名阅读；最新工作稿不回退。只在私有测试环境验收。B1 完成不代表 B 整体或公共运营完成。先审后发分支尚未实现时必须明确拒绝，绝不能将观察期账号当正常账号发布。

B1 不启用未确认的自动灌水限制；不接大模型；不把公开读取实现当作最小治理已完成。前端样式仍是评审版。

## 2. 已核实的代码约束

- draft.Store.Write 和历史清理均先锁 accounts 所有者行，保存事务内同时写当前草稿、修订及幂等结果。
- draft_revisions 采用 24 小时逐次、之后按天保留至 30 天，当前修订豁免。因此预览不能只依赖一个可能被清理的历史修订引用。
- A 标题上限 200 个 Unicode 字符、正文上限 1 MiB UTF-8，请求上限 2 MiB；已有 Cookie、精确 Origin、JSON、请求 ID 和 no-store 中间件可复用。
- HTTP 契约与路由双向覆盖，不可提前把未实现端点加入正式契约。新增契约必须和实现、错误反例测试一起交付。
- 恢复工具遍历数据库表并对全字段做指纹，不限于旧表名单；新增表仍需实际恢复验证，不能仅凭工具动态发现就宣称已覆盖。

## 3. 最小模型职责（表名为设计建议）

| 实体 | 内容与约束 | 目的 |
|---|---|---|
| publication_previews | owner、draft、源修订、固定标题/正文/简介/标签、内容摘要、创建/失效信息、消费结果关联 | 固定作者检查的内容；未提交正文与 A 历史清理独立 |
| works | 稳定 UUID、owner、唯一 source_draft_id、最后正式版本号、当前展示指针、作者隐藏、历史开关默认 false | 一个工作稿绑定一个作品，身份不随标题改变 |
| work_versions | work_id + 连续 version 唯一、完整不可变内容、发布时刻、来源 preview、内容摘要 | 正式版本可独立于预览清理而存在；不引用可变工作稿当正文 |
| publication_mutations | owner + mutation_id 唯一、operation、规范化载荷摘要、固定结果 ID/版本/提交时刻 | 超时重放得到原结果，同 key 不同载荷拒绝 |
| review_tasks | 绑定具体正式版本的后审任务、状态、首次等待时间、处理信息 | 后审待办与正式版本同事务建立，不能漏任务 |

这些是 B1 必需职责，不预建完整 C 的评论、举报、通知或通用事件平台。后续先审提交、处置、复核和观察期表在相应链路设计迁移中加入。固定预览和正式版本分别保存内容会增加一份短期副本，换取明确生命周期；不提前建设共享内容仓库或引用计数系统。

B1 的元数据准备由专门发布表单完成，预览将其完整持久化；未进入预览前刷新表单的未提交简介/标签是否恢复，应在前端接入时明确提示或本机保护，不得假称 A 已自动保存这些新增字段。标题/正文以指定的已保存修订为准，预览表单不悄悄覆盖它们。修改这些内容应回工作稿保存，再新建预览。

## 4. 准备预览

请求明确 draft_id、source_revision、简介、标签、发布授权确认及 mutation_id；所有者从会话取得，不接受客户端 owner_id。后端重新检查归属、源修订及字段，锁顺序保持 owner→draft→相关业务行。取源修订和复制预览内容在一个事务内完成，与 A 清理共用 owner 锁。

若源修订已清理，明确返回 source_revision_unavailable，提示重新读取并预览，不能擅自使用当前修订。若修订仍存在，固定当时的标题/正文及这次元数据，返回 preview_id、内容摘要和用于展示的固定内容。工作稿后来变新不使固定预览自动失效。

此阶段不生成正式版本、不入后审队列、不让匿名读者发现预览。预览 ID 不是访问凭据，每次读取仍校验账号。有效期为 24 小时。首期容量保护每账号每小时最多创建 30 份新预览，幂等重试不消耗额度；此限制不是内容质量评价。维护任务每次有界清理 100 份过期且未消费的正文，保留小型幂等记录防止旧 ID 复活；已消费预览不被清理。

## 5. 确认发布的原子事务

客户端发送 preview_id、mutation_id 和 expected_publication_sequence（预览时作品的最后正式版本号，首次为 0），不重新上传正文。

1. 校验请求/会话后开启事务，锁作者账号行；所有变更作者观察期的操作以后必须先锁同一目标账号行。事务内再读有效账号策略，不能信任预览时的状态。
2. 查询幂等结果：同 key 同载荷返回原提交确认；同 key 不同载荷返回 mutation_id_reused。先查成功结果再检查预览有效期，避免成功提交后因重试过晚被误报失败。幂等返回不重新开放作品。
3. 读取并锁本人预览、关联草稿及已有作品。已经消费的同一预览，即便使用另一 mutation_id，也返回同一结果，不产生新正式版本；不得触发新的发布副作用。
4. 对尚未消费的预览，检查有效期、授权确认、当前归属及标签状态。标签若已被停用，明确提示重新准备，不自动换成其他标签。
5. 在事务内以唯一 source_draft_id 创建或取得作品。核对预期正式序号；作品已被另一发布推进则返回 publication_conflict，保留工作稿和预览，要求查看最新发布状态再明确决定，不能静默追加版本。
6. B1 只允许已支持的正常账号分支；观察期或已有前审待办时明确拒绝并提示，不绕过前审。后续 B3 按相同事务边界接入前审流程。
7. 写下一正式版本、推进正式编号及展示指针；不改变作者隐藏。写 review_tasks 后审待办、绑定预览消费结果、写 publication_mutations 固定确认。
8. 全部成功才 COMMIT 并返回。任一写入失败全部回滚，不存在已发布却没有审核待办的成功结果。不在锁内调用外部 HTTP、SMTP 或模型。

不同设备同时首次发布，即使用不同预览和 mutation_id，也由账号锁、唯一草稿绑定及预期版本号共同防止重复作品或无意识连续版本。相同正文是否值得发布新版本不靠自动质量判断；新的明确发布仍需基于最新正式序号再次确认。

账号锁是沿用 A 的首期一致性选择，牺牲同作者并行写入吞吐；事务需短小并监控等待/死锁。死锁/提交响应丢失都可能需同 mutation_id 重试，不能以新 ID 假定前次失败。以后优化锁粒度需证据，不先引入分布式锁。

## 6. HTTP 契约草案（未注册）

| 方法与路径建议 | 身份 | 主要语义 |
|---|---|---|
| POST /api/publication-previews | 登录作者 | 从指定已保存修订固化预览；创建幂等 |
| GET /api/publication-previews/{id} | 登录作者 | 读取本人固定预览，不得跨账号 |
| POST /api/publications | 登录作者 | 消费预览，原子发布并建立后审待办 |
| GET /api/works/{id} | 匿名可访问 | 读取当前允许展示的正式版及安全元数据 |
| GET /api/works/{id}/versions/{number} | 匿名可访问 | 仅在当前展示或历史阅读获准且未受限时提供对应正式版 |

页面链接建议 /works/{uuid}，特定版本 /works/{uuid}/versions/{n}。路径和错误码在正式 OpenAPI 交付时冻结，不能将本节当作可调用服务。

首次发布身份在发布事务内分配；未来首次前审提交时在提交事务内分配，不在仅打开预览时创建空作品。此为技术建议：作者未提交前不会被系统制造待审作品，预览也不暴露公共链接。若影响产品展示再共同确认，不凭草案宣称用户已经批准。

成功响应固定包含 publication_result（work_id、version、published_at、review 状态的提交时结果）；界面之后单独读取当前访问状态。不能用重放的“当时公开”状态覆盖已经隐藏或受限的现状，不在幂等结果里复制全部正文。

错误沿用结构化 error + request_id：400 invalid_input；401 authentication_required；404 resource_not_found（不存在和越权统一）；409 mutation_id_reused/publication_conflict/nickname_required/source_revision_unavailable/unsupported_publication_state；410 preview_expired；413 payload_too_large；429 rate_limited；503 service_unavailable。拒绝时不要向匿名请求泄露资源是否存在或处置原因。数据库失败不得清 Cookie 或让作者误以为已登出。

版本号沿用 JavaScript 安全整数上限，与既有修订协议一致；日期使用明确 UTC 时间戳。标题沿用 200 字符、正文沿用 1 MiB；简介 300 字符、初始六个风格标签已确认，不擅自放大容量。

## 7. 读者访问与前端

统一服务端访问判断：作品存在且作者公开、无作品级限制、目标正式版本正常，且目标为当前展示或历史阅读已开启。被处置版本不进入读者时间线，旧链接不返回其标题、正文、简介或标签。待审/驳回/撤回节点仅作者可见。B1 未提供历史列表前不以临时固定数组冒充版本时间线。

公开页与 API 均执行同一规则，SSR HTML、分享卡片和版本链接都不能走旁路；不得先发送所有正文再由前端隐藏。沿用 no-store，初期不接 CDN 内容缓存；后续若缓存须另做权限失效设计。公开页默认 noindex，不把默认不收录误称为访问控制。文本用转义渲染，禁止将用户正文作为 HTML 执行。

已加载正文不主动替换；新的获取遵守新状态。发布/隐藏等 HTTP 失败不假报成功，保留工作稿。确认发布在途时禁重复点击，同时仍以服务端幂等兜底。超时沿用 mutation_id，结果确认后再读取当前作品状态。发现草稿新修订可提示继续旧预览或返回新稿，不自动换内容。

## 8. 迁移与部署

新增 B 表，不修改既有 drafts/draft_revisions 语义，不把 A 恢复草稿自动绑定原作品。新外键使用 BINARY(16)，关键唯一性和查询索引在迁移中落实；展示指针归属由事务和可行的组合约束保护，不能靠客户端传正确版本。

沿用 goose 逐次迁移，不假定 MySQL 多条 DDL 能全部回滚。新增表迁移必须检查部分失败后的恢复方式；上线前备份，验证 A 旧库升级与旧草稿读取/保存。回滚应用可保留新增表和 B 数据，不通过 Down 直接删除真实内容；具体部署顺序另留操作记录。

测试只能写 writing_test；使用真实 MySQL 验证事务与并发。新增表纳入备份往返指纹恢复；不能只跑一次 HTTP 成功就部署公众环境。

## 9. 实现前/后的关键验收

| 场景 | 预期 |
|---|---|
| 固定 R18 后保存 R19，再清理 R18 | 预览仍是 R18；发布 R18；工作稿保留 R19 |
| 清理先完成，才请求不存在的 R18 预览 | 明确要求重新准备，不自动改用 R19 |
| 相同 mutation_id 同载荷并发确认 | 相同 work/version/确认时刻，只有一个版本及一项后审任务 |
| 不同 mutation_id 消费同预览 | 同一发布结果，无重复副作用 |
| 两预览同时首次发布同草稿 | 只有一个作品；另一个基线过期明确冲突，不自动追加 |
| 版本写入后注入后审待办写失败 | 全部回滚，无成功确认、无半发布版本 |
| 提交成功但响应丢失，之后作品被隐藏 | 重试仍查到原发布确认，但不把作品重新公开 |
| 预览后账号进入观察期 | 确认按事务内最新策略判断，不直接公开 |
| 非本人读取预览或提交 | 统一不可访问，不泄露正文或作品信息 |
| 历史权限关闭/版本受限 | 页面、API、SSR/分享元数据都不给历史内容 |
| A 库迁移及重启/备份恢复 | 旧草稿可读写，新增正式版本、幂等确认及后审任务完整 |

日志仅记录请求 ID、动作、资源 ID 和脱敏错误码；不记录正文、标题、简介、邮箱、Cookie、原始 SQL 或 DSN。记录发布失败/延迟、事务冲突、后审积压与最老等待时间，告警不带内容。
