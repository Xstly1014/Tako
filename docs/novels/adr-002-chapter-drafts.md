# ADR 002：章节身份与工作副本隔离

2026-11-03，N1-B进行中，业务基线longform-business-spec.md。用户已确认恢复副本作为独立的新章节草稿，原章不覆盖；本ADR不把它解释成正式发布。

## 已确定工程决策

- Chapter有稳定ID，私密建章不分配正式序号；正式顺序只在N2发布事务分配。章节ID由书／账号／原请求／操作类型稳定派生，首次同步时确认归属，重复请求不能多建章节。
- 冲突恢复新建独立章节及其工作稿，recovered_from_id关联来源，原章和原稿保留。新章是否正式发布仍由作者决定，不自动替换公开内容或追加正式序号。
- 复用现有DraftRepository、AuthorizedDrafts、DraftSynchronizer与DraftEditor的CAS、固定原请求、加密本机暂存机制，不再复制一套正文同步器。Chapter作用域放在服务端Store与App受控工具中，不让客户端owner_id判权。
- 增加novel_chapters、chapter_drafts、chapter_draft_mutations、chapter_draft_revisions，使用组合外键绑定书／章／作者，一章一个工作稿。旧drafts表完全不增加章节字段；旧读取／列表／保存／恢复／历史和中篇发布源物理上无法读取章稿。这样已发布旧服务镜像回退也不会把章稿混入中篇。
- 私密章稿API按书作用域操作并从服务端验证稿件的章节归属，Store内部只允许固定的中篇／章稿三表映射，绝不接收客户端表名，仍用既有Draft/WriteResult语义，当前阶段无正式章发布。旧幂等输入编码完全保留，仅章节请求把书／章目标加入散列，防止老回执变成mutation_id_reused。
- 章稿历史使用独立chapter_draft_revisions，复用原维护算法，维护任务分别清理两组表，既有24小时细、30天分层保留继续适用，当前修订与恢复副本不被清理。
- App章节加密域与中篇、书籍资料请求域隔离；上下文绑定owner／书／本机稿，服务端再以不可变的稿件与章节关系约束归属，旧密文不改格式、不生成新钥覆盖旧数据。本机目录可离线找到已缓存章稿；未知结果沿原请求，不替其他账号同步。
- 原编辑器章节模式不展示中篇准备发布入口，且服务端独立拒绝经旧接口发布章节。退出前未同步计数应纳入章稿，不因新页面遗漏。

## 必须验证

旧中篇读写／回执兼容；同账号跨书跨章与跨账号不可读写；旧路由和publication-previews无法读取章稿；目录不含正式序号；首同步／重试／并发不多建章节；历史分层清理；密文跨作用域搬运拒绝；离线重开／换号锁定与冲突保留。迁移回滚仅独立合成库，现有3300不清数据。副本验收：原章节数不被重命名／覆盖，恢复产生一个新的私密章；原请求重放不会再增加章，旧发布入口拒绝两份章稿。


## 调整依据与本机过渡

最初本机未发布方案把章稿放旧drafts的可空列；审查发现旧二进制回滚没有过滤，会混读章节。这一方案在推送前撤回。确认本机和独立测试库的章节数为0后，按已保留的旧迁移撤回临时0015，再应用最终独立表0015。原账号／中篇稿／作品核对不变，不存在真实章节迁移或丢弃；未在已有真实章稿的库直接改写迁移。旧方案检查点仅在忽略的.runtime留存，不是最终交付。

结构回滚在有章稿或私密书籍时拒绝执行；正常代码回退保留新表和数据。回退会暂时失去新入口，但不能把私密章稿当中篇读取／发布。后续涉及工作稿公共字段的迁移，须同时核对两组明确表结构，不能依赖LIKE随未来表变动自动更新。
