# 长文交付计划与验收矩阵

日期：2026-11-03。基线：[业务规格](longform-business-spec.md)。N1-A私密资料与N1-B私密写章已实现，实际通过项分别见[书籍复盘](../reviews/private-novels-review.md)和[章节复盘](../reviews/private-chapter-drafts-review.md)。本表仍是分期验收要求，不代表真机或N2以后全部通过。

## 1. 分期与入口开放条件

| 阶段 | 纵向交付 | 退出条件／公开边界 |
|---|---|---|
| N0 规格 | 已确认权利、工程假设、失败矩阵和角色手册 | 用户关键决策已记录；当前阶段不改运行代码 |
| N1 私密开书与写章 | 物理模型 ADR、迁移、书籍资料稿、章工作稿、App 私密创建／编辑／恢复 | 真实 MySQL 所有权、CAS、兼容迁移；App 自动化；不出现假的阅读／完结／追更入口 |
| N2 首发与逐章阅读 | 固定预览→首章／追加→回执→目录→阅读；书／章隐藏恢复；最小限制撤销 | 公共入口权限、序号竞争和未知回执验证；接入最小长文列表便于发现，元数据搜索可后接；完结按钮暂不可用 |
| N3 续读与完结纠错 | 私密跨设备位置；不可逆完结；平台指定章整改授权、提交、人工审核 | 完结和整改同时可交付，不能只开放前者；正文变化和位置冲突可解释且不丢输入 |
| N4 书架追更与站内提醒 | 加入书架并追更、独立关闭、有效订阅、新章事件、隐藏期汇总补发 | outbox 重试、幂等、动态权限和观测通过；此阶段前不显示可用的追更承诺 |
| N5 章讨论与发现收口 | 按章两级评论、元数据搜索、频道分页与 App 完整闭环 | 删除／屏蔽竞争、旧中篇兼容、长目录和真实服务集成；按实际证据发布验收记录 |

阶段可以拆小提交，不能把整条链路的必要纠错放到无期限以后。N2 首次公开正文前必须已有最低限度的限制、撤销和原因管理；不等待自动治理制度。N1 ADR 若发现复用方案影响已有中篇，先做兼容验证，再建新接口。

这些阶段是主开发后续方向，不给并行端新增源码认领。并行端继续 CI/M1/C2 和设备，双方读 progress 后再协调交叉触点。每个运行阶段推送记录准确源码 SHA 和设备任务；纯规格更新不要求重打包。

## 2. N1 实施前 ADR 必答

1. 书／章独立表还是与旧 Work 的显式关联；如何保证旧中篇仍是一稿一作品，不伪造整书正文。
2. 章工作稿的类型和绑定：旧客户端能否误保存／误发布，离线本机目标如何迁移，既有密文如何兼容。
3. 正式章序号的事务锁和唯一约束，预期目录修订、原请求作用域及回执不可串用。
4. 评论、处置、预览和回执如何关联稳定章 ID；不靠字符串多态绕过外键／授权。
5. 最小数据迁移／回滚：升级前存量中篇、草稿、评论数量和关系核对；不能靠清库通过。
6. 精确 HTTP 契约、分页游标、Unicode／字节限制、错误码、旧 App 行为和生成类型。
7. 与并行端 C2/M1/auth／构建配置的实际触点；在确定共享文件写入方后修改，不直接扩其认领。

ADR 是工程裁决，不要求用户逐项选择数据库设计；只有新业务权利、跨账号行为或丢失风险才提问。

## 3. 每条接口的交付包

实现、OpenAPI、明确错误和必要失败验证同批交付。必须运行路由覆盖、请求和响应契约测试、相关真实 MySQL 集成，以及受影响 App 模型／组件测试。声明生成从唯一契约源进行，不能只手改类型或补说明。

候选语义类别（尚未作为 API 发布）：未登录 401；资源不可见 404；可解释的目录／状态／位置竞争 409；已过期预览 410；参数错误 400；限流 429；暂不可用 503。精确错误标识由 N1 确认。权限失败是否 403 或 404 必须与现有不泄露规则一致。

单独记录：模型测试、DOM 页面、真实 HTTP＋MySQL、编译／CI、实际设备、外部服务和恢复演练。列表中标“设备”的由同事执行，主开发提供源码和用例，不操作 USB、不构建 APK。

## 4. 失败与权限验收矩阵

P0：安全、跨账号或内容丢失，阻塞受影响交付。P1：必需业务正确性，阻塞对应阶段入口开放。下表均为待执行预期。

| ID／阶段／优先级 | 触发 | 必须结果 | 最低证据／负责人 |
|---|---|---|---|
| N01／N1／P0 | B 读取／保存／导出 A 的书或章工作稿 | 不泄露正文与存在性，不产生写入 | HTTP＋MySQL／主开发 |
| N02／N1／P1 | 开书／建草稿响应丢失后原请求重试 | 返回同一对象，不多建书或章 | HTTP＋MySQL／主开发 |
| N03／N1／P0 | 中篇稿冒充章稿、跨书替换目标 ID | 服务端拒绝，不产生串归属内容 | 契约＋MySQL／主开发 |
| N04／N1／P0 | 升级已有本机草稿存储格式，含未同步密文 | 可恢复旧内容；失败不删库、不换密钥抹去内容 | 存储自动化／主开发；设备／同事 |
| N05／N1／P0 | A 离线暂存后切 B，再重登 A | B 不可读取或代同步；A 明确恢复 | 模型／主开发；设备／同事 |
| N06／N1／P1 | 两端修改同一章稿 | CAS 冲突保留双方内容，不能覆盖 | MySQL＋页面／主开发；设备／同事 |
| N07／N2／P1 | 预览后继续改工作稿，再发布 | 发布固定快照；新工作稿原样保留 | HTTP＋页面／主开发 |
| N08／N2／P1 | 预览到期／被篡改／跨账号提交 | 明确拒绝并保留输入，不能发出不匹配快照 | 契约＋MySQL／主开发 |

| N13／N2／P1 | 章发布成功响应丢失，退出重进 | 原 ID GET 恢复，不生成第二次 POST／新章 | 服务＋页面／主开发；设备／同事 |

## 5. 真实 App 验收移交

每次运行代码推送在 ../handoff/device-requests.md 写：源码 SHA、后端版本／契约、依赖环境、不需重跑的旧项、需要验证的变化、预期保留与失败提示。并行端冻结其实际整合树，自己记录包哈希、设备、系统、服务入口和通过／失败／未执行。

重点不是每轮让用户亲测，而是同事验证中文／表情／长粘贴、离线暂存和杀进程、键盘遮挡、系统返回、跨页状态、切账号、授权失败及跨设备竞争。主开发提供故障注入和自动化，但不能把它们当原生结论。若缺设备，继续独立开发，相关设备门槛不虚报通过。
