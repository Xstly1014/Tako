# N4：书架、追更与站内新章提醒

2026-11-05。主开发连续业务包；基线main `8d89a7e`，API0.26、迁移24。本文件是开发规格，不是完整交付报告。N4-A服务内核API0.27/迁移25与严格客户端已实现，本机运行仍0.26/24，App页面和提醒尚待同包后续工作，证据见阶段记录。已确认权利来自[长文业务基线](longform-business-spec.md)N-D04/08/13；前置N3的实际完结/整改链路已接工程，真机与真实用户结果仍分开记账。

## 1. 这次要解决的问题

读者找到一本连载后，需要能再次找到，并知道作者真正发布了哪些新章。当前App“我的书架”和底部“消息”仍是未开放入口，不能把中篇收藏冒充长文追更。作者修订旧章、修改资料或隐藏恢复，不应不断打扰读者；读者关闭追更后，也不能继续收到旧订阅积压。

首版只做免费站内链路：目录加入书架并追更→我的书架→新章站内提醒→当前可读目录/正文。沿用已有登录、真实公开判权和私密续读。不上邮件、手机系统推送、实时WebSocket、算法推荐、打赏、章节评论、未读章节数或完读率；通知未读与正文阅读进度分开。

## 2. 已确认规则

| 事项 | 约束及来源 |
|---|---|
| 加入 | 按钮必须明确“加入书架并追更”，两个状态原子受理，不能收藏成功但追更失败 |
| 关闭 | 可单独关闭追更，作品继续在书架；关闭停止后续投递，已有消息保留 |
| 移出 | 明确提示同时关闭追更，保留私人续读位置，不删阅读回执、本机未同步位置或已有站内消息 |
| 重新加入/开启 | 新订阅代次，不继承旧代次尚未投递积压，不补普通历史章 |
| 首发来源 | 只有一章第一次实际落正式版才有新章事件；预约、待审、驳回、撤回没有 |
| 非首发 | 修订、资料更新、完结、指定整改、旧章恢复均不产生新章事件 |
| 审核乱序 | A第1章晚于B第2章通过，A是新的实际首发提醒，但不改章号；不能用最大章号判断“已经提醒过” |
| 隐藏期 | 整书隐藏时新增的正式章暂缓；恢复后未提醒且当前可读的章汇总一条，不能逐章轰炸或重复恢复重发 |
| 既有记录不可读 | 书架保留安全占位；消息动态判权，不展示旧标题、正文或私密处置原因，不能获得永久访问权 |
| N-D18 | 用户2026-11-05确认：隐藏期未提醒的新章后来恢复可读时补首次提醒；已提醒的旧章不重复 |
| N-D19 | 用户2026-11-05确认：不可读期间只允许关追更/移出；首次加入和重新开启须当前可读，旧关系及位置保留 |

两项边界已获用户明确答复；后文Q1/Q2分别引用N-D18/N-D19，不能再作为待决项拖延。

## 3. 关系与订阅代次

书架属于会话账号与稳定书ID，不属于作者笔名、某章或某个正式修订。不存在的本人关系返回空状态，不能据此探测别人是否收藏或书是否存在。私人列表只查当前账号，客户端不传可信owner_id。

关系至少含在书架、追更开关、关系修订、订阅代次和本代起点。首次加入开追更；关闭不退架；移出同时关闭。重新开启/再加入生成新代次。新代次起点必须是与发布事务可确定先后的事件边界，不仅比较客户端时间或章号。

两端操作采用关系修订条件。A关闭后，B的旧界面不能无提示重新开启；冲突刷新当前状态再由本人选择。一个原请求重试返回原受理结果，不能因现在状态改变再执行一遍。回执不是当前状态；查询现状失败仍保留已确认结果。

本轮不自动清理书架关系或站内消息，不借用续读回执的30天规则。移出可保留必要关系/代次墓碑与原回执，避免旧请求复活订阅；这些元数据不包含正文。未来保留期限要单独裁决，不暗中删除用户数据。

## 4. 真实入口与页面任务

复用原型结构，不新建第二套个人中心。精确页面布局在接线前按ui-deai核对，若超出原型框架再单页评审；本规格不是新的视觉设计稿。

| 入口 | 主任务 | 次级信息与返回 |
|---|---|---|
| 现有书籍目录 | 判断是否继续读/加入书架并追更 | 未登录转既有登录，回原书后仍需明确点击，不登录成功即自动加入 |
| 我的→我的书架 | 找到已加入作品并继续读 | 紧凑真实列表；追更开关/移出为管理动作，保留返回“我的” |
| 既有底部消息 | 看站内新章提醒，选择进入作品 | 只开放新章类，评论/关注/系统推送仍不可用，不造数字 |
| 消息详情/目标 | 查看当前可用新章或回目录 | 返回消息列表保留位置，不把历史通知链接当权限凭证 |

书架至少显示当前可读书名、作者、连载/完结及追更状态；封面仍按现有素材规则，不新增上传业务。不可读作品仅安全占位、关闭/移出等已允许动作，不复用上一次加载的标题。列表分页，不一次读所有作品；排序采用明确加入顺序，不在首版伪造“最近阅读/未读章数”。

有本人续读位置时复用N3的跳转和冲突选择；没有则进入目录。位置指向不可读章时不擅自跳过。书架与已存在中篇收藏分域，旧接口、旧“我的收藏”不改变对象类型。

消息行使用当前安全作品资料、提醒类型、时间、已读状态。点击标记消息已读不等于读完章节；失败可以重试，不能改写续读位置。暂不可读时安全占位且可返回，不把404当删除关系。若提供全部已读，需绑定本次已加载列表边界，不把并发到达的新消息一并吞掉；首版可先仅逐条已读。

加载、空态、失败重试、会话失效、冲突、禁用、受理未知和受理后刷新失败均要接实际状态。动作区域沿用主题色与现有控件，不增加大块彩色说明卡、装饰箭头或版本字段。

## 5. 新章事件与订阅资格

复用已有 `chapter_release_events`，不从书籍updated_at、最大章号或轮询客户端猜新章。当前事件有稳定章ID/书ID/序号/实际首发时间，但缺少可靠订阅边界及投递状态；这些是N4需要补的能力，不是已实现事实。

工程候选：为首发事件增加服务端单调序列，订阅开始时在同一本书发布锁边界内取已提交事件水位；发布事务仍只写一个事件，不逐粉丝投递。事件可以有空号；同书追加/审核与订阅先后以锁和提交结果裁决，不依赖毫秒时间相同的偶然顺序。历史事件升级后不补给新订阅。

投递资格同时满足：事件在本代开始之后、该账号当前仍在书架且追更、代次未变、事件尚未对该代发送、目标当前可读。加入/开关与投递竞争必须有确定线性化点，不能只在任务扫描时查一次资格，随后无锁写通知。关闭先完成则旧代次不得再投递；通知先完成则它作为已有消息保留。旧代次积压不能自动绑定到重新加入的新代次。

作者可以给自己的已公开作品加入书架；作者不能据此查看其他读者关系、通知或个人轨迹。首期不增加粉丝排行榜或作者可见的个人追更列表。

## 6. 隐藏期汇总与动态权限

事件在隐藏期间已落库，不代表已经通知。恢复必须区分真正未提醒的新章与旧章；“恢复可见”本身不是首发事件。一次恢复可汇总多个当前可读的新章，重复恢复不能重复通知；如果只有一章也使用同一安全流程。不同账号起点/代次可能不同，汇总范围不能是整本书一份通用计数。

汇总投递必须冻结它覆盖的稳定首发事件集合或等价确定范围，并原子记录这些事件对本订阅代次已覆盖。只记录最大章号会漏迟到过审的第1章，只记最大事件序列却跳过不可读洞，也可能永久漏提醒。N-D18已确认不可读洞等待可读后补首次提醒，不能用最大水位把它当已结束。

长隐藏期可能有很多新章：维护分页不能把一个汇总拆成几十条消息，也不能在每次扫描时反复扩写已读消息。具体持久模型需要在实现前用“多页事件、部分不可读、并发恢复和退订”实验定稿；不预先承诺单个SQL或固定批量数即可正确。

通知只持久安全ID引用/覆盖关系与时间，不复制书章标题或正文。列表和点击均重判书、章、当前正式版本可读性；已经发送不授予永久阅读权。当前标题修订后使用当前安全标题；受限时不显示旧标题、引用段落或私密原因。关闭追更不删除历史消息，撤销限制不重新产生已发事件。

## 7. 服务、持久化和契约交付

下表为整个N4能力清单。书架关系/列表/原请求已落OpenAPI0.27并连运行时校验、生成类型和真实HTTP/MySQL；消息/投递仍未实现。书架迁移已使用25，仅隔离测试库升级，当前运行环境未升级。精确书架路径及状态见ADR004，不把整个能力清单当已交付。

| 能力 | 必要边界 |
|---|---|
| 本人书架关系GET/列表 | 会话归属、空关系不泄露、稳定分页、不可读元数据归零 |
| 加入/关追更/开追更/移出 | 修订条件、载荷绑定原请求、明确副作用、保续读、Q2待决 |
| 原请求GET | 本账号/本书/操作匹配，历史受理与当前状态分开 |
| 本人消息分页/逐条已读 | 不可跨号，动态安全投影，幂等已读不改阅读进度 |
| 首发事件及投递维护 | 事务内事件、资格与代次校验、唯一约束防重、崩溃恢复 |
| 积压健康 | 当前可处理积压与等待不可读分开；最近成功/失败和耗时，不输出账号/正文 |

优先复用MySQL事务和现有独立维护进程，不新增消息队列服务。扫描和投递分小批，有确定游标、唯一键、任务成功/重试记录；多实例同时跑或在写通知后进程退出，也不能重复发送。待可读不作为无限故障重试，不用一条永远隐藏的书卡住所有书。

锁顺序要与现有作者发布、治理及读者位置写入相容，实测交叉操作而不是假设没有死锁。避免发布持有作者锁时逐粉丝拿账号锁；维护不得为汇总读取未提交私稿。数据库事务失败不留下“关系已开但无起点”“通知已有但事件未覆盖”等半状态。

App持久未知操作复用已有账号隔离、加密和原请求恢复原则，不能为书架另造不受切号保护的全局队列；不把服务拒绝和网络未知混成一个错误。断网阅读仍按既有规则，本轮不扩成离线整书。退出规则沿用原确认：注销未完成时不假称已退出。

## 8. 一个连续包内的开发次序

1. **业务/数据契约定稿**：已收齐Q1/Q2；小规模事务实验固化首发水位、订阅代次、不可读洞与汇总覆盖，写ADR；不创建假消息界面。
2. **书架纵向链路**：关系/列表/原回执API＋契约＋真实MySQL；实际App目录/我的书架、加密未知恢复、现有N3续读接入；不可读状态及跨端冲突一并验证。
3. **新章提醒纵向链路**：事件边界/维护/安全消息API＋消息页；正常首发、乱序审核、隐藏汇总、退订/重开、崩溃/多worker和动态权限一并验证。
4. **同源码收口**：App/实际HTTP/MySQL整条、旧中篇/续读/发布回归，迁移保旧数据与非空拒回滚；恢复演练；阶段复盘和交接；设备可用时由主开发补匹配APK证据。

这是一个连续业务包的内部次序，不要求用户逐接口说“继续”，也不把每个接口单独做一轮Git提交。共享契约可设检查点，但只接服务内核时明确未完成App/完整提醒；推送在可核验阶段进行，每次fresh同步同事分支/进度。主开发负责非Agent全域与设备，同事继续Agent评测，不重复旧设备任务。

| 编号 | 场景 | 必须观察到的结果/层级 |
|---|---|---|
| N4-01 | 重复加入/响应丢失重开 | 一份关系、一个原受理；App重挂只查原结果，不能悄悄换ID再POST |

| N4-03 | 两端旧修订开关/移出 | 至多合法当前操作受理；冲突后由本人决定，旧重试不复活关系 |
| N4-04 | 关闭/移出与投递竞争 | 以提交顺序决定通知是否已存在；不投给已关闭的旧代次 |
| N4-05 | A退订后B章发布，A重开 | 新代次不收旧积压；后续真正新章正常收到 |
| N4-06 | 首发与加入并发/同微秒 | 按事务边界确定一次资格，非客户端时钟/章号推算 |
| N4-07 | 第2章先公开、第1章后通过 | 各一次真实首发提醒，目录号稳定，不漏第1章 |
| N4-08 | 旧章修订/改资料/完结/整改 | 零新章事件，零新章提醒；N2/N3存量回归 |
| N4-09 | 隐藏期多页新章，恢复两次 | 本代应补且可读章一条汇总；覆盖不重发，不逐分页轰炸 |
| N4-10 | 汇总中某章仍不可读，后来恢复 | 按N-D18等待可读后补首次提醒；不得泄漏标题/正文或因最高水位漏洞 |
| N4-11 | 投递后章/书受限或隐藏 | 通知仍可安全占位，不泄漏旧标题；点击不能绕过判权 |
| N4-12 | 多worker/受理后崩溃重启 | 通知与覆盖关系事务一致，唯一约束/重试不重复；真实MySQL |
| N4-13 | 书架分页、空态、不可用锚点 | 自己的稳定列表，无别人关系、旧标题或草稿；刷新有明确动作 |
| N4-14 | 跨账号GET/已读/原请求、切号迟到响应 | 拒绝/安全空态；新账号不渲染或提交上账号数据 |
| N4-15 | 移出书架/标消息已读 | 私人续读与本机未同步候选原样保留，读完率不变化 |

| N4-17 | 持久化失败/加密记录损坏 | 不能先POST再补记；保留可恢复证据，不清库换钥解围 |

| N4-19 | 升级已有库/旧App/撤销迁移 | 原书、章、位置、回执保持；有新业务数据时不破坏性回退 |
| N4-20 | 维护失败与恢复 | 可定位积压/失败，隐藏等待与错误区分；不是假“已送达”指标 |

## 10. 如何判断这包有业务价值

三栏账本继续使用：代码能力、已验证行为、真实用户结果。前两栏可用合成账号、实际HTTP/MySQL和App适配器推进；真实读者是否从书架续读、是否因提醒回来需外部样本，不用测试计数冒充留存。没有设备时持续推进无依赖部分，但不能以DOM截图关闭Android加密/生命周期/网络切换尾项。

P1／写对应行为前：Q1/Q2已确认，汇总持久模型仍须实验定稿。P1／宣布N4工程交付前：上述连续链路与失败矩阵通过，OpenAPI/生成类型/真实数据库/维护齐全。P0／受影响移动创作对外开放前：旧C1与本包账号/原生持久验证退出。P1／公开运行前：另议生产入口/容量与离机恢复；本次不启动ECS、不发外部通知。
