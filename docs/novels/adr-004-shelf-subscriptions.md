# ADR004：书架关系与首发订阅边界

2026-11-05。N4-A服务内核决策，基线c122c47。源码API0.27/迁移25；后续N4-B已保卷升级本机API0.27/25并接实际App书架/恢复。通知覆盖/多页汇总模型仍属于后续N4，不在本ADR冒称已实现。

## 决策

书架新建 `novel_shelves`，主键为会话账号和稳定书ID，与中篇favorites分开。在架、追更、关系修订、订阅代次、起始首发水位及加入/更新时间分别存储。退出保留墓碑，不删除私人阅读位置；已有续读表及其回执不改变。

四个明确命令：join从不在架进入在架并开追更；follow从在架且关闭进入新代次；unfollow只关闭；remove同时退架和关闭。不符合前置状态或旧修订返回409 novel_shelf_conflict，不静默把重复新命令当重新订阅。原mutation完全相同则始终重放原回执；回执与现状不同是预期，不拿历史join回执恢复现在的架。

`novel_shelf_requests`按账号+mutation唯一，hash绑定书/操作/完整输入，持久化不可变元信息回执。跨书、改操作或载荷拒复用；跨账号/错书查询回执404。请求结果没有标题或正文，不套用续读30天清理规则。

复用chapter_release_events的章级唯一首发事实，增加内部release_sequence自增唯一索引及书+序列索引。新订阅开启时读取同书已提交最大序列。不能用最大章号（晚过审的早号会漏），也不能用客户端时间或同微秒时间比较。该序列只服务内部订阅边界，不返回客户端，避免暴露不可读首发的内部水位；历史回填序列不承诺重建旧事务的真实时间排序，升级前没有订阅关系，所有历史事件都在新订阅起点以内。

当前契约：GET `/api/my/novel-shelf` 本人分页；GET/POST `/api/my/novel-shelf/{id}` 当前关系/明确操作；GET `/api/my/novel-shelf/{id}/requests/{mutation}` 查询原结果。既有发布开关默认关闭时全部503；匿名401、跨号回执404、CAS/载荷冲突409、非法请求400。精确schema以OpenAPI为准。

## 事务与可见性

写关系采用READ COMMITTED，锁序为读者账号→同书共享锁→本人关系；作者发布/治理已有同书排他锁。始终先查原回执再执行业务，已受理后即使书隐藏也能查原结果。加入/重新开启获得书锁后重查正式资料及至少一章当前可读；关追更/移出不要求公开，不读私稿。

不能沿用默认REPEATABLE READ做无锁读取：先查回执会建立早快照，随后等书锁时别人可能已经隐藏或首发。拿到锁再从老快照查资格/起点会错。真实MySQL测试让另一个事务持书锁并隐藏，join阻塞后必须看到提交后的不可读并拒绝。发布与订阅的同书边界串行，其他书的全局序列空号不构成问题。

后续投递必须同样遵守锁序并重查当前代次；本批并未实现worker，不声称此条件已经由投递端验证。禁止发布事务在持作者/书锁时逐粉丝拿读者账号锁。

## 列表与安全投影

本人在架列表每页12条，按加入时间/书ID倒序；关追更不改变加入位置，重新加入更新加入时间。游标锚点验证本人历史关系；移出后的同锚点仍可翻页，再加入改变锚点则400要求刷新。一个事务内先取有界关系，再批量查同页可读正式书籍，避免全量粉丝/书扫描和每行查询。不可读时book=null，保留本人关系，不复制旧标题。无关系GET返回0修订/空时间，不泄漏作品存在性。

## 兼容与验证

迁移25不改章ID、章号、首发时间与原外键；新增表独立，旧App不需要理解它们。有关系（包括已退架墓碑）或请求回执时禁止down，不能为降级删用户数据；无新业务数据时可移除新增表/内部序列，保留旧事件。

实证见[N4阶段记录](../reviews/n4-shelf-follow-stage-review.md)：完整Go race/vet/HTTP/MySQL和请求响应/路由覆盖，关闭期间真实首发后再开启的水位、跨号/幂等/CAS/不可读/分页/位置保留，以及隔离迁移升降与非空拒绝。内核检查点只含协议客户端和生成声明；后续N4-B已接页面与加密未知恢复，通知投递仍待，不承诺未实现的提醒。
