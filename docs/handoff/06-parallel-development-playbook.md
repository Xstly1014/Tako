# 06 · 并行开发端手册

2026-11-03。适用于用户已安排的另一台电脑/现有Codex；不是创建新代理或擅自扩大分工的授权。与AGENTS、tako-collab及用户最新指令一起使用。

## 用户本次执行意图：完整业务包，减少重复收尾

用户明确要求“一次性多规划一些开发任务，拓展业务开发速度”，指出小任务频繁Git/文档/CI流程浪费上下文。这项调整同样适用于并行端，不仅是主开发。

- 一次规划后续几个完整业务包，连续完成当前一个。小提交用于恢复和审查，不等于每做一张表/一个接口/一个按钮就结束工作、写新阶段报告、等用户再说继续。
- 当前包须说明谁从哪里进入、最终得到什么结果，覆盖已确认范围内的前后端/契约/失败/必要验证。不能把已有能力反复包装成新阶段，也不能以扩大批次为由顺带加未授权业务。
- 常规实现选择自主推进。只有新业务权利、数据丢失/跨账号、不可逆结果、必要范围变化或归属冲突需要与用户argue；等待答复时做独立部分，不停掉整个包。
- 认领范围保持用户既有分工：主开发连续完成N2发布→最低治理→发现/目录/阅读；并行端继续自身作者业务/完整验收/CI/设备。主开发N3/N4规划不表示已转交并行端，新增独立业务需先协调。

## Git、验证与文档节奏

1. 开始工作读最新目标/规则、实际双方分支和进度。对同一已读SHA不重复全文读技能/报告；有新增才读相关差异。缓存不能把失败的fetch冒充同步成功，不能从“无新提交”推断对方未提交范围空闲。
2. 本地可频繁做可恢复小提交；远程推送优先在必要的可消费共享接口检查点、完整业务包收口，或用户明确要求时。长任务可有远程恢复检查点；推送检查点之后继续包内开发，不自动等待下一条“继续”。
3. 每次实际推送仍fresh fetch，核对main/自己远端/对方实际分支、共享接口与文件归属，普通合入/验证/推送。禁止force/整份ours-theirs或手拼生成声明。减少重复流程不等于跳过并行保护。
4. 新的独立提交若不影响当前包，可以记录待审并在集成窗口批量处理；确定安全/数据丢失/契约冲突及时处理。不要让无关文档/测试提交不断打断自己的已授权业务，也不能声称待审内容已合入。
5. 开发中运行必要局部回归；有运行变化/失败/未解决问题再扩大检查。包收口执行所需完整验证，纯文档不重复跑全量Go/App。CI等待时可继续独立工作，尚未完成的结果不写成通过。
6. 一个业务包维护一份规格/复盘并更新自己的parallel-progress，不为每个小步骤另造报告。CI绿灯可随下一次必要提交补录，不为一行结果默认再推一次；不靠重复推送原码碰运气。

## 同步接收与交接

本文件由用户明确要求发布。并行端下次同步后先阅读本页、[主开发进度](primary-progress.md)及自己的实际分支记录，在自己的parallel-progress注明已读取本项用户要求，以及当前完整业务包/下一检查点。无需专为“已读”单独推送，和下一次必要提交一起记录；主开发不得代写成对方已确认。

接口/数据/契约交接必须有真实来源，主开发接手整合不代表你已改动其环境。设备仍按用户暂停/恢复指令，不自动安装、操作USB或连接ECS。编译、模型、DOM、真实HTTP/MySQL、恢复、包、设备和真实用户结果分别记账。

主开发的同等执行规则见[05手册](05-development-playbook.md)，当前连续队列见[N2规格](../novels/n2-publication-reading-spec.md)。本页调整执行粒度，不替换已确认业务权利与源码归属。
