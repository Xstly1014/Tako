# 业务优先（Business First）

## 定位

本 skill 只提供**全局判断标准**，不规定开发流程、不插入固定步骤、不改变任何既有工作方式。它只回答一个问题：

> 我现在交付的东西，是"能演示"，还是"能承接真实业务"？

任何阶段都可以拿它自检，尤其是准备说"完成了"的时候。

## 核心命题

业务实现与 demo 的差别不在代码量，而在于**是否处理了真实世界不可协商的约束**：脏数据、并发、失败、存量兼容、他人依赖、长期可维护。

## 六个 demo 化信号（命中即需纠正）

1. **只走通快乐路径**：没有失败分支、没有异常输入处理、没有超时与重试。
2. **数据是假设出来的**：默认输入干净、字段齐全、时区正确、量级很小。
3. **状态只活在内存里**：重启即丢；没有持久化、没有幂等、不考虑重复提交。
4. **接口只服务自己**：没有契约、没有兼容或版本考虑、没有对调用方的错误语义。
5. **写完即结束**：不验证真实场景（边界、并发、回放），没有任何可观测手段。
6. **为了演示而硬编码**：魔数、跳过校验、临时绕过、用 TODO 代替实现。

## 业务完整性判据

在宣布某个功能完成前，逐条确认：

- **失败会怎样**：错误是否被明确处理并给出可理解的反馈，而不是静默吞掉或直接崩给调用方。
- **重复与并发会怎样**：幂等、顺序、竞争条件是否被考虑。
- **老数据与老调用方会怎样**：是否有兼容或迁移路径。
- **别人接手会怎样**：边界条件、接口契约、不显然的技术决策是否有据可查。
- **上线后怎么知道它坏了**：是否有可观测手段能定位问题。
- **这条需求解决了谁的什么问题**：如果说不清楚，说明做的是技术演示而不是业务实现。

## 克制条款（同等重要）

"业务完整"不等于"功能膨胀"。以下行为同样偏离目标：

- 把没被要求的需求"顺便"做了。
- 为想象中的未来场景提前引入抽象层。
- 用复杂的通用方案替代当前明确的简单实现。
- 以"业务考虑"为名扩大改动范围。

判断标准：**为已知的真实约束付出成本，不为想象中的需求预付成本。**

## 正反例对照

| demo 化写法 | 业务化写法 |
|---|---|
| 直接 `data["name"]` 取值 | 明确缺失字段时的业务语义（默认值 / 报错 / 跳过） |
| 创建接口不防重 | 重复提交时的幂等键或唯一约束 |
| 新字段直接覆盖旧结构 | 先兼容读取、双写或迁移，再切换 |
| 出错只 `print` 一行 | 错误可追溯，调用方拿到明确结果 |
| 需求没写清就按猜的做 | 先指出歧义，给出默认假设并说明影响 |

## 自问三句

1. 这个实现如果明天接入真实用户和真实数据，第一个坏掉的地方在哪？
2. 我现在的取舍，是因为需求如此，还是因为这样写最省事？
3. 如果要向业务方解释这个改动，我能说清它解决了什么吗？
