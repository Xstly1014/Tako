# 协作记录与同步协议

## 各自维护进度

主开发维护 `docs/handoff/primary-progress.md`，并行端维护 `docs/handoff/parallel-progress.md`。稳定使用双方已确认的角色名，不根据电脑、模型或分支名称猜身份。历史 `parallel-ci-results.md` 只保留阶段证据；主开发汇总项目入口，另一端不同时重写。

进度记录至少包括下列实际信息，字段可随任务简化；不用创建空模板或伪造时间戳/确认：

| 信息 | 必须说明什么 |
|---|---|
| 身份/版本 | 维护方、更新时间和时区、本地分支、实际 HEAD、记录是已发布还是仅本地 |
| 观察 | 已检查的 main/对方分支及准确 SHA、对方进度文件版本；不是仅写“已同步” |
| 认领 | 解决哪个业务问题、精确文件/接口范围、用户已分配或待协调、明确不归本端的共享触点 |
| 集成依赖 | 输入/输出、兼容规则、谁改调用方、谁生成契约/锁文件、谁负责最终集成与包构建 |
| 验证 | 哪个提交实际跑过哪些层级、结果/产物位置；哪些只是此前证据或未执行 |
| 状态 | 例如开发中、工程检查通过、待对方接口、待审、已推送未集成、已进主线未入包 |
| 风险/交接 | 阻塞哪一部分、优先级、负责人、解除条件、对方需确认的最小问题和下一步 |

自己的下一次提交 SHA 在提交前未知，写已验证的基线/源码范围并在提交说明或后续观察中绑定实际提交，不编造自引用 SHA。“对方已收到/认可/审查通过”须有可追溯确认，不能由推送成功推导。

## 同步时读什么

1. 查本端未提交改动与上次观察记录，fetch 后确认实际远程 refs。
2. 看 main 与双方功能分支，而非只看 main。读取**对应 ref** 上的对方进度、阶段复盘及增量，防止本机旧文件冒充对方最新声明。
3. 对每个 ref 找共同祖先，分别检查 `共同祖先..本端`、`共同祖先..对方` 的变更，加上本端工作区。不能把 `HEAD..对方` 的净差异全当对方新改动；本端独有文件可能在其中显示删除。
4. 比较路径之外，核对账号/会话代次、请求幂等、参数语义、契约/测试分类、依赖、迁移、构建输入等共享行为。无文本重叠仍可能有语义冲突。
5. 仅新的事实、范围变化、风险或需要用户决策时更新对话；持续工作仍要按宿主要求及时报告，不用无变化快照刷屏。

可用 Git 操作示意（先用真实 ref/SHA 替换参数；保持各命令结果可检查）：

```text
git status --short
git fetch origin --prune
git for-each-ref --format=%(refname:short) refs/remotes/origin/
git merge-base HEAD <peer-ref>
git diff --name-status <merge-base> <peer-ref>
git diff --name-status <merge-base> HEAD
git show <peer-ref>:docs/handoff/<peer-progress-file>
```

这些命令不构成授权绕过。fetch 超时/认证失败时，记录失败及最后已知 SHA，继续不依赖新事实的独立工作；在完成必要的新鲜度核对前不推送到可能被推进的分支。按环境的正常网络/凭据方式恢复，不打印代理凭据、token 或完整含敏感信息的错误。

## 接口与文件移交

把边界写成“小合同”：提供方给什么、消费方验证什么、错误/未知状态怎么保留、谁修改哪个入口、什么事件触发重验。已明确授权的范围自主做，不为每次改行重复审批；涉及新权利或跨归属的变更才重新协调。

对同文件的分区协作，写出双方触点及集成人，即使预计可自动合并也要核对完整结果。共享锁文件、生成声明、迁移序号不要分区手拼。对方不可达不等于可接管；只推进本端独占部分，保留待交接的调用点和可独立运行的验证。

## 阶段收口

检查实现与规格、失败语义及必要反例；更新自己的进度/阶段复盘，保留未完成项的优先级与退出条件。推送前重新核对包括本端远程分支在内的 refs，再按现有授权集成、验证和推送。CI 成功后记录被检查提交；后续仅文档变化可沿用未变代码的证据，但明确代码基线。不要为记录 CI 结果而伪造“新提交已跑全量”。
