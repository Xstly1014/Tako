# 交叉审查与批评性建议

## 审查对象与独立性

明确作者、审查者、被审 SHA、比较基线、关联规格、文件范围与验证条件。审查者通过原始差异、调用方和必要实验得出判断，不先接受作者的完成结论。自己开发后换分支自查不算另一位 agent 独立审查；报告校对也不等于代码审查。

只读读取对方工作，实验使用隔离 worktree/合成环境，不运行未知破坏命令，不污染对方工作区/数据库。能确定的问题不因对方未回复而省略；看不到的工作和无法运行的服务明确为未验证。

## 重点判断

- **业务兑现**：真实用户从哪里进入、得到什么结果？页面是否实际接线？是否误把 Web/API、基础模块、旧包或原型能力记为新 App 交付？
- **身份/保留权利**：当前会话是否授权每次读写/恢复，切号/失效/迟到响应如何处理？持久化什么、何时清理，是否改变用户确认的草稿/评论/发布策略？
- **未知结果与竞争**：发送前是否保留原标识，重试是否同一请求，回执是否被错误当作现状？并发、存储失败、提交成功但丢响应、进程终止如何保留可确认状态？
- **集成兼容**：接口传入的“修订/已保存”究竟是本机还是服务器确认？新测试是否进入分类，依赖/类型/迁移/构建输入是否一致？不能只检查 Git 冲突。
- **证据真实性**：核对准确命令、代码基线、环境、结果及未覆盖项。组件夹具不等于真实 HTTP，Node SQLite/加密不等于 Expo 原生存储，构建不等于设备验收，合成数据不等于真实运营。

只追与本次交付有关的真实风险，不为假想规模扩大架构、治理或测试范围。

## 发现的写法与裁决

每条有问题再写：

```text
[P1][确定缺陷] 简短标题
位置：文件及准确行号；被审提交。
触发：可复现操作、竞争次序或输入条件。
影响：具体业务错误、数据/权限后果及影响范围。
证据：原始代码关系、复现或检查结果；区分推断与实测。
建议：最小修复方向与能证明已修复的验证出口。
```

P0 用于紧急安全/数据损失或关键完整性问题，P1 为阻断本阶段核心行为的缺陷，P2 为有证据的局部正确性/可维护性问题，P3 为非阻塞改进。按实际影响判断，不将所有缺测试都标为 P0，也不把有数据损失证据的问题降格为风格建议。待核实风险给出需要哪项证据，不冒充已复现；一般偏好明确标为建议。

作者在自己的进度/后续提交中回应：接受并给修复 SHA/验证，或用契约、原始代码及实验反驳。审查者复核实际修复，记录已解决、仍存在或结论撤回，不靠“已处理”文字关闭。审查报告可保留历史发现并追加复核记录，不能删证据让报告显得全绿。

技术争议优先用小实验和明确验收条件解决；业务权利/数据损失/跨账号或范围取舍交用户决定。给用户的 argue 应包含具体代价与替代方案，不用礼貌性附和、笼统“有风险”或权威口吻替代证据。意见不一致不授权审查者接管对方代码。
