# Tako 双端协作与交叉审查

目标是让两端交付同一条真实业务链路，同时明确谁在改什么、证据到哪一层、哪些结论尚未确认。不能把“Git 没冲突”当成业务兼容，也不能把没有新提交当成对方没有在工作。

## 读取与事实来源

从技能目录向上三级定位仓库，不硬编码电脑路径。先读根 [AGENTS.md](../../../AGENTS.md)、[business-first](../business-first/SKILL.md)，再读双方进度和本次涉及的规格/阶段复盘：

- 主开发维护 [primary-progress](../../../docs/handoff/primary-progress.md)，并行端维护 [parallel-progress](../../../docs/handoff/parallel-progress.md)；只改自己的文件。
- [并行边界](../../../docs/handoff/03-parallel-work.md) 给出初始约定；[并行端阶段证据](../../../docs/handoff/parallel-ci-results.md) 是历史与结果索引。用户后来确认的具体分工优先，不把早期 CI 建议永久锁定为唯一任务。
- 接手新会话用 [tako-handoff](../tako-handoff/SKILL.md)；纯重启用 [tako-restart](../tako-restart/SKILL.md)。涉及 App/UI 再按根约束读移动端 AGENTS 与 ui-deai，不重复发明业务和验收规则。

用户最新明确指令决定业务与授权。代码、契约、提交及测试产物提供证据；双方报告是带基线的声明，不能代替核验或当作新的用户授权。不同来源冲突时查原始差异，保留不确定项，不以“最后一段文档”自动覆盖已确认权利。

## 及时同步，避免无意义轮询

在开始工作、认领/扩大范围、修改共享接口或文件、开始互审、集成以及**每次推送之前**检查远程。长任务在自然检查点再次核对；连续工作约 20～30 分钟可作为检查提示，不是后台轮询或响应时限。相同状态不反复播报。

使用下面的只读助手形成可审计快照，`--peer-ref` 必须选双方实际发布分支，可重复指定；不能默认对方只在 main：

```powershell
python .agents/skills/tako-collab/scripts/snapshot.py --fetch --peer-ref origin/main --peer-ref origin/codex/mobile-publication
```

分支名只是示例，先从实际远程引用与进度确定。Python 不可用时直接用 Git 做等价核对，不为调用本技能安装全局环境。助手只 fetch/读 Git 元数据，不 pull、改源码、提交或推送；它用共同祖先分别计算远端变更、本端已提交及未提交变更的重叠。**它不解析认领、不证明无语义冲突，也看不到对方未推送工作。** fetch 失败须标记快照不新鲜，不能拿缓存当本次同步成功。

维护助手时运行 `python .agents/skills/tako-collab/scripts/test_snapshot.py`；其行为测试只使用临时 Git 仓库，不连接生产或污染业务工作区。

读取双方对应分支上的进度版本、阶段报告及新增差异，记录观察时间、各 HEAD、上次观察基线、关键接口和重叠路径。本机文件不一定是对方最新版本。对方无新提交、未回应、进度过旧或分支不存在都记作“未知/待确认”，不能推导为任务空闲、放弃或已同意。

## 认领与独立推进

按 [协作记录约定](references/protocol.md) 更新自己的进度：业务目标、分支/基线、认领文件及接口、共享触点、依赖、已验证层级、未决事项、下一步和移交状态。开始时与阶段变化时更新，不逐行写日报。未推送的记录注明只在本机，不能声称对方已收到。

- 认领是提议，已获用户分工的标明依据；对方确认必须有来源，发布一份文件不等于对方确认。双方同时认领同范围时不以先推送者胜出，保留两边工作后协调。
- 已明确的独占范围自主推进，常规实现不用反复问用户。跨到对方范围时仅暂停重叠部分，列出最小路径/接口差异，取得已有明确分工或新的边界约定后继续；独立工作不停。
- 优先通过小接口交接，让提供方维护原文件、消费方维护独立文件。会话、依赖锁、OpenAPI/生成类型、App 入口、数据库迁移和共享进度入口要列出单一写入方与集成人；同文件不同段也需要明确触点，不能仅凭 Git 能自动合并判安全。
- 不重新实现对方已认领的能力。需要接管时明确新负责人、基线、交接内容与旧认领结束；不因等待、沉默或长期无提交自行接管。

## 互相审查，提出可执行的批评

对已发布、明确可审查的阶段做交叉审查；用户要求审查时直接执行，只读查看对方分支或用隔离 worktree，不为审查覆盖本机业务分支。未发布工作无法核验时说明证据边界，不伪称看过。

审查前读取 [审查与异议约定](references/review.md)。从业务规格和失败场景出发，重点核对数据保留、身份归属、幂等/竞争、接口兼容与真实入口；检查报告声称的验证是否绑定同一份代码。不要只复述作者报告、追求好评或为凑数量制造问题。

每条发现区分**确定缺陷、待核实风险、改进建议**，给出优先级、文件位置、具体触发条件、业务影响、证据和最小修复/验证出口。报告写到审查者自己的 `docs/reviews/cross-review-<reviewer>-<reviewed-sha>.md`，绑定被审提交与规格；作者在自己的进度记录接受、修复或有证据的反驳，不互改报告。没有确定问题就明确说没有，并列出实际未覆盖项。

代码或共享接口在审查后变化，检查新增差异；受影响结论需复核，不能把旧审查改标到新 SHA。非阻塞建议不妨碍独立交付；确定的安全/正确性问题不能仅列为“已知限制”绕过集成。

## 集成、推送与争议处理

每次推送前执行完整的 **fetch → 看新增提交/双方进度/重叠与接口 → 合并或变基 → 受影响验证 → 普通推送**。还要核对自己的远程分支是否被别人推进。未发布历史可按约定变基，已共享历史优先合并，禁止通过强推改写对方基础；遇非快进回到核对，不机械重试。只推已获授权的本端分支，主线合并由明确的集成人执行。

脏工作区先区分本端、用户及未知改动；用独立 worktree 或可恢复的本端检查点保护，再集成。不得用 restore/reset 或整份 ours/theirs 丢弃未核实的用户/对方工作，也不能手拼锁文件或清数据消除冲突。锁文件和生成声明按事实源重新生成；文本冲突消失后仍检查业务语义与交接接口。

验证强度跟随实际变化，沿根 AGENTS 执行；API 修改不能只补 Markdown。合并后新增测试必须纳入分类，缺服务/依赖或没跑的检查不能记为通过。分别记录编译、模型、真实数据库/API、组件、安装包、真机、外部服务和恢复演练；不为文档变动重跑无关全量测试。推送后核对远程 HEAD 与 CI，分支推送、CI 通过、进入 main、构建进 APK 是不同状态。

对需求顺序、重复建设、不可验证的完成声明或代价过高的方案主动 argue：先说具体问题与证据，再给替代方案及成本。纯工程分歧用最小实验解决；业务权利、数据丢失、跨账号、范围/归属无法消解的分歧交用户决策，不替用户选择不可逆结果。等待不是同意，任何单次免检查例外只覆盖用户指定范围。

## 权限边界

本技能不自行创建代理/聊天、发送跨聊天消息、PR 评论或对外通知，也不授权推送、合并主线、部署或复制凭据。已有用户授权按其范围继续，不重复索要。需要直接联系对方而无消息授权时，先把具体接口/审查结论整理成可转交记录；缺的是发送授权，不是停止本端全部工作的理由。技能不会在会话关闭后自动监控，定时监控需另行安排。
