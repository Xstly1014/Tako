# 前端重做与布局协商（UI Layout Rework）

## 定位

用于这个局面：**功能已跑通，前端是 AI 自由发挥的产物，用户认为"不是我要的"**。

它修的不是审美，是三个缺失：重做前没有取证；布局从未成为被确认的契约；AI 不会反对用户，沟通退化成了许愿。

**不适用**：局部样式微调；已有完整设计稿且不需要拆解的情况。

## 三条第一原则

1. **接口与业务层冻结。** 只换表现层，不改 API、数据模型、业务语义。
2. **没有确认的布局，不写一行 UI 代码。**
3. **argue 是义务。** 不允许顺着用户第一句话直接实现。

---

## 阶段 0：判断走哪条路（先于一切）

先问一句：**"有没有一张图、一个产品，照着做你就满意？"**

| 答案 | 路径 | 做法 |
|---|---|---|
| 有明确参照（Figma / 截图 / 竞品） | 参照对齐 | 按下方七个维度拆解参照物，逐页列出对应关系与不可照搬项，直接产出契约 |
| 只有模糊感受 | 完整协商 | 走阶段 2–4，逐页提案与 argue |

参照对齐不等于放弃判断：照搬会与平台规范或触达条件冲突时（如把桌面布局塞进移动端），仍必须指出冲突并给替代方案。

---

## 布局的七个维度（所有讨论的坐标系）

任何一页的"布局"都必须谈到这七项，缺项即未对齐。跳过它们直接谈"风格"，讨论必然退化成审美争吵。

| 维度 | 必须定到 | 判定 |
|---|---|---|
| 栅格 | 列数、最大内容宽度、断点 | 各断点下不变形 |
| 间距节奏 | 基准档位（如 4/8）、区块间距 | 全站 ≤ 4 档 |
| 信息密度 | 首屏条数、行高、每屏信息量 | 与主任务一致 |
| 层级 | 字号档位、主次对比、视觉焦点 | 3 秒内找到主操作 |
| 导航模型 | 侧栏 / tab / 面包屑、层级深度 | 任一功能 ≤ 3 层可达 |
| 状态布局 | 空 / 错 / 载 / 无权限 / 超长文本 | 每种都有确定占位与动作 |
| 适配策略 | 断点行为、App 安全区与手势 | 不是简单缩放 |

---

## 阶段 1：取证与基线（不动手）

产出「前端现状清单」：页面 → 路由 → 调用的接口 → 现有交互与状态；组件树；状态管理与请求层边界；样式入口与 token；平台外壳（Web 的 layout、App 的导航与安全区）。

同时留基线：旧代码开分支或打 tag，关键页面截图存档。验收时要对照"原有功能入口一个不少"。

明确只替换哪一层：

| 层 | 处理 |
|---|---|
| 数据 / 业务逻辑 | 保留 |
| 页面结构与交互骨架 | 重做 |
| 视觉样式 | 重做 |

Web 与 App 共享代码时（RN / Taro / 响应式 Web），先确认复用边界。**默认只共享逻辑，不共享布局。**

---

## 阶段 2：锁定主任务与偏差

不接受"不好看""不够现代化"。一次只问 3–5 个：

1. 每个核心页面的主任务是什么？（一句话，必须由用户确认，**不许代答**）
2. 有没有"对"的参照物？具体哪里对？
3. 现在最不能忍的三处具体是什么？
4. 用户主要在什么设备、什么场景下用？
5. 哪些是核心页面，哪些次要？

产出「偏差清单」，每条必须可验证：

- ❌ `主色调太重`
- ✅ `列表页首屏必须看到 8 条以上记录，当前只有 3 条`
- ✅ `新增记录从进页面到提交 ≤ 2 次点击，当前是 4 次`

---

## 阶段 3：逐页提案与 argue（核心）

一次只谈一页。每页交付四件：

1. **ASCII 线框图**（必须画，不许只用文字），至少覆盖七个维度里的状态布局。
2. **七个维度的具体取值**。
3. **交互路径**：从进入页面到完成主任务几步。
4. **取舍**：这个方案主动放弃了什么。

### 提案规则

- 给 2 个（最多 3 个）方案，明确推荐一个并说明理由与代价。**不许说"都可以""看你喜好"。**
- 禁止模糊词。每个决定落到具体值：列数、间距档位、断点、tab 数、首屏条数、字号层级。

### 反对规则

用户意见会带来可观测代价时——首屏信息变少、主任务步数增加、平台规范冲突、移动端不可触达、可访问性下降——**必须直接反对**，说清三件事：

1. 会坏在哪
2. 代价是什么
3. 我建议怎么做

然后由用户裁决。裁决后按用户执行，并把该取舍写进决策记录。**反对必须指向可观测后果，不能指向个人审美。**

### 每页当场确认，不攒到最后

每页结束当场向用户确认该页，记下「已确认」后才能进入下一页。攒到全部谈完再一次性签字，前几页的结论一定会被遗忘。

协商记录写 `docs/ui-layout/<平台>-<页面>.md`：线框图、七维度取值、采用与被否决的方案、用户裁决的争议点。

---

## 阶段 4：汇总复核（不是重新讨论）

全部页面确认后，只复核**跨页一致性**，不重开布局讨论：

- 导航模型全站一致
- 间距与字号档位统一，不超过约定档数
- Web / App 差异项明确，不是同一套布局缩放
- 每页状态覆盖齐全

复核通过后输出「布局契约」总表：页面 / 线框图 / 七维度取值 / 平台差异。此后任何布局改动都要回到阶段 3。

---

## 阶段 5：执行

顺序：设计 token 与布局骨架 → 导航与路由 → 逐页替换（一次一页，可回退，新页面先挂旧路由，不整体删除）→ 补齐状态 → 响应式与终端适配。

约束：

- 禁止顺手改接口、业务逻辑或无关代码。
- 禁止擅自更换 UI 库或引入设计系统——先问。
- Web 与 App 分开设计：

| | 关注点 |
|---|---|
| Web | 断点、信息密度、悬停与键盘、URL 可分享 |
| App | 安全区、底部导航、手势、键盘弹起、滚动性能、弱网 |

---

## 阶段 6：验收

对照契约与阶段 1 基线逐页核对：

- 首屏条数、主任务步数、层级可达性符合契约
- 空 / 错 / 载 / 无权限 / 超长文本齐全
- 至少 3 档尺寸：Web（移动 / 平板 / 桌面）、App（小屏 / 常规 / 大屏）
- 数据来自真实接口，不是 mock
- Web：键盘可达与焦点顺序
- 对照旧版截图，原有功能入口一个不少

---

## 反模式（命中即停）

- 用户说完就"好的，我来重做" → 缺取证与协商。
- 一次甩整站方案 → 无法逐页 argue。
- 用户说"你看着办"就真自己看着办 → 必须给方案 + 推荐 + 代价。
- 只用文字描述布局 → 等于没对齐。
- 跳过七个维度直接谈"风格" → 讨论会退化成审美争吵。
- 攒到最后一次性签字 → 前面几页的结论会被遗忘。
- 为好看擅自换技术栈 → 越界。
- 重做 UI 时顺手改接口 → 越界。
- App 直接套 Web 布局 → 平台职责不同。

---

## 交付物

| 交付物 | 位置 |
|---|---|
| 前端现状清单 + 旧版基线 | 会话记录 / 分支或 tag |
| 偏差清单 | 会话记录 |
| 每页线框图与决策 | `docs/ui-layout/<平台>-<页面>.md` |
| 布局契约总表 + 确认 | `docs/ui-layout/contract.md` |
| 重做后的前端 | 代码 |
| 验收结果 | 会话记录 |

## 示例（阶段 3，主任务已在阶段 2 确认）

> **用户**：把首页做成卡片瀑布流吧。
>
> **Agent**：
> - **反对**。阶段 2 确认的首页主任务是"快速定位待处理事项"。瀑布流卡片高度不一，第二屏之后无法对齐扫描；移动端单列时首屏只能看到 2 条，低于契约要求的 8 条。
> - **方案 A（推荐）**：分组列表 + 置顶待办。首屏 8 条，主任务 1 次点击。
> - **方案 B**：双列等高卡片。首屏 6 条，适合浏览，不适合处理。
> - **代价**：A 视觉更"平"，B 更吸引但不服务主任务。
> - 你来裁决。

## 自检

- [ ] 每页都画了线框图，不是只有文字
- [ ] 七个维度没有缺项
- [ ] 每页都是当场确认，不是最后一次性签字
- [ ] 给的是"方案 + 推荐"，不是列完让用户选
- [ ] 反对时给的是可观测后果，不是审美判断
- [ ] 编码阶段没有擅自改布局、接口或技术栈
- [ ] 验收对照了阶段 1 基线
